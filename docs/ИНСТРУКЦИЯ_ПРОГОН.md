# Прогон: что, в каком файле и когда

Команды AutoCAD исполняются в том чертеже, который сейчас активен, —
командная строка в AutoCAD одна. Поэтому важно не «в каком файле команда»,
а **какой чертёж в этот момент активен**. Ниже каждый шаг помечен.

Участники:

| Роль | Что это | Что с ним делаем |
|---|---|---|
| **Донор** | файл, где лежит новый мастер-блок (`Комплект КП50 v1.51`) | только копируем из него блок |
| **Реципиент** | рабочий чертёж со старыми экземплярами | здесь грузим LISP и запускаем всё |

---

## Шаг 0. Подготовка реципиента

**Файл: реципиент.**

1. Откройте реципиент.
2. `СОХРАНИТЬ КАК` → копия (`recip-test.dwg`). Работаем в копии: прогон
   меняет чертёж.

## Шаг 1. Загрузить программу

**Файл: реципиент** (активен реципиент).

```
(load "D:/RepDblock.lsp")
```

**Проверка баннера — обязательна.** Должно быть:

```
RepDblock.lsp, сборка 72.7 — подмена динамических блоков.
Берёт из буфера новую итерацию семейства и заменяет ею старые вхождения:
создаёт варианты, обновляет вложенные определения, возвращает видимость
и динамические свойства, затем чистит старые определения.
Команды:
  +--------------------------------+------------------------------+
  | КОМАНДА                        | ЧТО ДЕЛАЕТ                   |
  +--------------------------------+------------------------------+
  | ПДБ / ПОДМЕНАБЛОКА (RDB)       | заменить семейство из буфера |
  | ПДБВЫБОР (RDBPICK)             | заменить по выбранному блоку |
  | ПДБОЧИСТКА (RDBCLEANUP)        | очистка старых определений   |
  | ПДБВОССТАНОВЛЕНИЕ (RDBRECOVER) | восстановление после сбоя    |
  | ПДБЛЕЧЕНИЕ (RDBHEAL)           | лечение паспортов динамики   |
  +--------------------------------+------------------------------+
  Подробно: (setq KG-TRACE-DETAIL t).
  Порядок прогона: docs/ИНСТРУКЦИЯ_ПРОГОН.md
```

Полная таблица команд — в `README.md`. В баннере должны быть все команды
от `RDB` до `RDBERR`; если таблицы нет или номер сборки другой, загружен
старый файл.

Если имя файла или номер сборки не совпадают — возьмите свежий `RepDblock.lsp`.

## Шаг 2. Снимок ДО

**Файл: реципиент.**

```
(setq KG-TRACE t)
RDBBRIEF
```

Это состояние чертежа до прогона: сколько определений, сколько `*U`,
сколько сирот. По нему видно, что именно изменилось.

## Шаг 3. Скопировать мастер-блоки — **непосредственно перед прогоном**

**Файл: донор** (активен донор).

1. `Ctrl+C` → указать базовую точку.
2. Выбрать мастер-блоки — **по одному на каждое семейство, которое нужно
   обновить** (`Комплект КП50К стойка v1.52`, `Комплект КП50К ригель v1.52`,
   `Комплект КП50 v1.51` — можно все сразу) → Enter.
3. Вернуться в реципиент.

Сборка 71.3 обрабатывает **все семьи, пришедшие из буфера, за один
прогон**: каждой семье — свой мастер, своя замена и свой отчёт. Если нужна
одна семья — скопируйте один блок.

Копирование делается последним, прямо перед `RDB`: так в буфере
гарантированно лежат нужные блоки, и ничто между копированием и вставкой их
не перезаписывает. Буфер обмена общий для всего AutoCAD, поэтому донор
после этого можно закрыть.

## Шаг 4. Запустить подмену (RDB)

**Файл: реципиент.**

```
RDB
```
*(также работают алиасы: `RepDblock`, `ПОДМЕНАБЛОКА`, `ПДБ`, `INTEGRATE`)*

Команда работает в **1 клик** без лишних диалоговых запросов: она автоматически освобождает имена, вставляет мастер-блок из буфера обмена, заменяет все вхождения старых версий (или одноимённого блока без версий), восстанавливает состояния видимости, атрибуты и очищает временные объекты.

Если из буфера пришло несколько семейств, каждая семья печатает свой
разделитель и отчёт:

```
--- Семейство 1 из 3: Комплект КП50К стойка v1.52 ---
```

Очистка — одна на весь прогон, её итог `=== ИТОГ ОЧИСТКИ: … ===` печатается
в конце.

*(Если требуется ручной выбор предварительно вставленного мастер-блока на чертеже, используйте команду `RDBPICK` / `ПДБВЫБОР`).*

Очистка встроена в конец `RDB`, отдельный запуск не нужен.

## Шаг 5. Снимок ПОСЛЕ

**Файл: реципиент**, сразу после того как `RDB` закончила:

```
RDBBRIEF
```

## Шаг 6. Только если команда упала

`RDBERR` печатает `Последний шаг` по копии, снятой в момент **последнего
падения**. Если в этой сессии команда уже падала, а потом отработала
успешно, поле покажет старое падение. Судить по нему, исполнялась ли
команда, нельзя.

**Файл: реципиент.**

```
RDBERR
```

Она печатает текст ошибки и шаг, на котором всё оборвалось. Запускать
имеет смысл **после** падения: до него печатать нечего («команда не
падала»). Ошибка запоминается и переживает следующие команды, так что
можно запустить и позже.

Если вместо ошибки сеанс закрылся целиком (AutoCAD исчез), ничего
специально делать не нужно: состояние возврата лежит в журнале рядом с
чертежом, и любая из команд (`RDB`, `RDBPICK`, `RDBCHECK`, `RDBCLEANUP`)
вернёт переменные и снимет временные вложения сама. Отдельная команда
`RDBRECOVER` (`INTRECOVER`, `ПДБВОССТАНОВЛЕНИЕ`) нужна, когда чертёж уже
открыт заново и команды ещё не запускались; после возврата журнал
удаляется, и повторный запуск просто печатает, что возвращать нечего.

## Шаг 7. Выключить трассировку

**Файл: реципиент.**

```
(setq KG-TRACE nil)
```

Иначе следующий прогон даст огромный лог.

## Что нового в сборке 72.1 (перенос динамических свойств)

* **Убран двойной перебор при переносе свойств.** Суб-замеры сборки 72
  показали: из 85.7 с шага «замена экземпляров» на 100 вхождений 72.7 с
  уходило на «замена: динамические свойства». Причина — на каждое
  сохранённое свойство заново перебирался весь список свойств экземпляра, и
  имя у каждого спрашивалось у платформы. Теперь имена читаются один раз
  (карта «имя -> свойство»), а значения, уже совпадающие с сохранёнными, не
  переписываются вовсе: запись свойства запускает пересборку анонимного
  представления, и пропуск ничего не меняющих записей экономит больше, чем
  один вызов.
* **Поведение и отчёты не изменились** — переносятся те же значения, строка
  «Перенесено динамических свойств N» остаётся (совпавшее значение тоже
  считается перенесённым: оно уже такое, как надо).
* **Новые суб-замеры** (при `(setq KG-TIMING t)`): «замена: свойства --
  карта имён» и «замена: свойства -- значения (работа)» — по ним видно,
  сколько уходит на разбор карты, а сколько на сверку и запись.

## Что нового в сборке 72.7 (чужие вставки не читают дорогие свойства)

* **Причина падения 72.6 найдена по автосохранению.** Семья 3 падала на
  первом чтении модели на `1200 из 1232`, handle `93173`. Это
  `*U`-представление **ригеля семьи 2**, а не стойки. Семья 3 читала
  динамику и вложенную видимость чужой вставки, которые ей не нужны.
  Живая проба 72.7 на копии автосохранения: для `93173`
  `want-foreign=no`, `want-own=YES`; модель строится без COM,
  `nested-vis` и `dyn-props` пусты, падения нет.
* **Первый полный снимок модели в обычном прогоне пропущен.** В `C:RDB`
  вставка и освобождение имён уже сделаны, `KG-PRERENAMES` задан, ветка
  `do-paste` не работает. Снимок в начале `KG-Integrate_Model` нигде не
  использовался, но читал все 1233 вставки на каждую семью — и именно на
  нём падала семья 3. Теперь он читается только в режиме `do-paste`.
* **Динамика, вложенная видимость, аннотативность и атрибуты читаются
  только у вставок своей семьи.** У чужой вставки остаются handle,
  определение, эффективное имя, пространство, слой и геометрия. В режиме
  семьи VLA-объект для чужой вставки не создаётся вовсе. Это убирает
  около 90% дорогих COM-вызовов на чтении модели и COM-обёртку с `93173`.
* **Остальные чтения — без дорогих свойств:** перепривязка вложенных,
  снятие старых определений, контроль, начальный снимок `C:RDB`, поиск
  мастер-версии. Им нужны только определения, имена, handle, пространство
  и геометрия.
* **Проверки**: 824/824, 59/59 (добавлены M11d–M11h), скобки, арность
  (372), имена (558), загрузка (54 команды / 344 имени). Живая загрузка
  72.7 — баннер на месте. На копии автосохранения без дорогих свойств
  собраны все 1232 вставки — ошибок и падения нет.
* **Журнал больше не теряет отчёт.** `-PURGE` печатает по строке на каждый
  удалённый блок; `NOMUTT` и `CMDECHO` этот вывод не подавляют. Поэтому в
  конце очистки печатается сводка `Очистка: снято блоков «*U...»: N,
  временных «~...»: M`, а полный отчёт по семьям повторяется в самом
  конце. Его можно скопировать из хвоста F2 или вызвать `RDBREPORT`
  (`INTREPORT`, `ПДБОТЧЁТ`) — без сотен строк очистки. Тот же отчёт
  автоматически сохраняется в `RDBREPORT.txt` рядом с чертежом; путь
  печатается в конце прогона. Если динамическое свойство не записалось,
  в отчёт попадут handle, имя и значение — до 30 строк.
* **Что проверить на живом прогоне**: полный прогон всех трёх семей.
  Ожидается 520 замен, 0 потерь, 0 ошибок. Семья 3 не должна доходить до
  чтения свойств `93173`. Если падение повторится — пришлите последнюю
  строку `[шаг]`, handle и путь `.sv$`: по ним видно, на каком этапе
  оборвалось уже новое чтение.
* **Что не меняется**: отчёт, имена, число замен и перенос свойств у своей
  семьи. Чужие вставки остаются в модели и учитываются в отчёте.

## Что нового в сборке 72.6 (имя `*U` без COM, сборка мусора)

* **Падение 72.5 на семье 2** случилось на 101-й вставке, хотя то же
  состояние незадолго до этого прочитало контрольное чтение: причина —
  накопленные COM-объекты, а не данные. На малом реципиенте 72.5 прошла
  все три семьи за 44 с — логика замены верна.
* **Имя `*U…` читается из паспорта по DXF** — расширенный словарь →
  `AcDbBlockRepresentation` → `AcDbRepData` → 340. Это убирает около двух
  тысяч COM-вызовов `EffectiveName` на каждое чтение модели (раньше имя
  читалось для каждой вставки, не только `*U`). На крупном файле паспорт
  есть у всех 691 верхней и 494–520 вложенных `*U`: 0 пустых, 0
  расхождений, 78 мс на 691 вызов. Если паспорта нет — прежний COM-путь.
* **Имя параметра видимости** читается по DXF: запись `BLOCK_RECORD`
  берётся по группе 330 примитива `BLOCK` (вместо `EffectiveName`,
  `vla-Item`, `vla-object->ename`; остался только ename вставки). Если словаря
  `ACAD_ENHANCEDBLOCK` нет, работает прежний запасной поиск по написанию;
  на крупном файле словаря нет ни у одной записи, так что поведение
  прежнее.
* **`(gc)` перед первым чтением модели каждой семьи и каждые 50 вставок**
  (было 200). Падение случалось до первой сборки.
* **Проверки**: 824/824, 54/54, скобки, арность (361), имена (548),
  загрузка (51 команда / 331 имя). Живая загрузка 72.6 — баннер на месте.
* **Что увидите в замерах**: «модель: вхождение -- вложенные состояния»
  должна заметно уменьшиться; остальные строки и отчёты не меняются.

## Что нового в сборке 72.5 (быстрее чтение модели и карта ссылок)

* **Чтение модели больше не ходит в ActiveX за каждой мелочью.** Имя,
  слой, точка вставки, поворот и масштабы берутся из данных объекта
  (entget); COM остаётся для вставок с нестандартной нормалью и для
  анонимных представлений `*U…` (там группа 2 служебная, имя читается с
  родителя). Внешняя ссылка определяется по флагам записи блока, поле
  `is-dynamic` не запрашивается — оно никем не читается.
* **Обход определений — по DXF** (tblobjname/entnext), без vlax-for;
  COM — только на имена `*U…`.
* **Шаг перепривязки вложенных читает только вхождения** — определения
  ему не нужны.
* **Карта ссылок строится по снимку содержимого определений**: один
  проход DXF перед шагом перепривязки (669 определений / 4284 вставки —
  0.9 с на крупном файле), дальше карта читает снимок. Правка
  определения сбрасывает его запись.
* **Что увидите в замерах**: новые суб-замеры «семья: снимок содержимого
  определений», «модель: определения», «модель: вхождения», «модель:
  вхождение -- геометрия / вложенные состояния / динамические свойства».
  Сравнивать с прошлым прогоном (934.6 с) по строкам «чтение модели»,
  «карта ссылок», «держатели».
* **Поведение и отчёты не изменились.** На живом крупном файле снимок
  сверен с прежним сканом по всем 669 определениям — 0 расхождений.

## Что нового в сборке 72.4 (паспорта динамики: перепривязка и лечение)

* **Дефект прошлых сборок.** Уборка перед PURGE «снимала метаданные
  динамики» — удаляла деревья словарей у вставок внутри определений
  вместе с паспортом вставки (расширенный словарь →
  `AcDbBlockRepresentation` → `AcDbRepData` → ссылка 340 на запись
  базового определения). Без паспорта имя вложенного динамического
  блока переставало разрешаться: в Свойствах вместо «Стойка КП50»
  стояло `*U462`.
* **Теперь деревья не снимаются.** Ссылки 340 переводятся на записи
  действующих одноимённых определений: кандидаты освобождаются,
  паспорта живых вставок целы. Если действующего имени нет — паспорт
  не трогается, вставка называется в отчёте. Флаг `KG-CLEANUP-STRIP`
  (по умолчанию t) отключает шаг целиком.
* **Новая команда `RDBHEAL`** (`INTHEAL`, `ПДБЛЕЧЕНИЕ`) — лечение уже
  испорченных чертежей: повреждённым вставкам паспорт собирается заново
  (под-словарь + объект данных + ссылка 340). База берётся по карте
  здоровых паспортов, при её отсутствии — по «близнецу» (такое же
  строение, здоровый ребёнок на том же месте); при неоднозначности
  паспорт не пишется. Здоровые паспорта не трогаются. Как лечить:
  копия файла → `RDBHEAL` → сохранить → проверить Свойства вложенного
  блока.
* **Проверено живым прогоном** (крупный «Реципиент», копия):
  `RDBHEAL` — 36 из 36 повреждённых паспортов; после сохранения и
  переоткрытия — 520 здоровых / 0 повреждённых, контрольные цепочки
  верны (`*U462` → «Стойка КП50», `*U465` → «Закладная в полость
  стойки», `*U466` → «Стойка КП50 контур»), `AUDIT` — 0 ошибок.
* **Поведение прогона не изменилось** — та же замена, те же отчёты; в
  очистке вместо снятия печатается «паспорта динамики: перепривязано
  ссылок N, вставок M» (и, если есть, «паспорта динамики без замены
  оставлены у вставок: K»).

  семейства i из N) ===`; цифры сделанных семейств не теряются при
  падении на следующем.
* **Поведение не изменилось** — та же замена, те же отчёты.

## Что нового в сборке 72.2 (суб-замеры переноса свойств)

* **Живой прогон 72.1 на крупном чертеже:** шаг «замена экземпляров» на
  100 экземплярах 85.7 с → 80.1 с; карта имён почти ничего не стоит, а
  куда уходит остаток — по прежним суб-замерам не видно. Поэтому перенос

* **Новые суб-замеры** (при `(setq KG-TIMING t)`): «замена: свойства --

### Видимость вложенных блоков у определений без итерации

Определение без итерации в имени («Стойка КП50», «Закладная в полость
стойки») подменяется целиком, и состояния видимости его вложенных блоков
сбрасываются в значения по умолчанию новой версии. Теперь они снимаются до
освобождения имён и возвращаются после перепривязки:

```
[шаг] снимок состояний вложенных блоков
[шаг] снимок состояний вложенных блоков: определений 7, состояний 27, без параметра видимости 61
...
[шаг] возврат состояний вложенных блоков
[шаг] возвращено состояний вложенных блоков: 5 в определениях 1
Возвращено состояний вложенных блоков в определениях: 5
  из них не найдено в новой версии: 0
  из них записать не удалось: 0
  из них запись не подтвердилась чтением: 0
Определений, в которые возвращены состояния: 1
  Закладная в полость стойки
```

Как читать:

* **`без параметра видимости N`** в снимке — сколько вложенных вставок
  осталось без состояния. По этому числу «снято 27» сводится с «в определении
  9 вложенных вставок». Если у определения со вложенными блоками стоит
  `состояний 0`, а это число равно числу вложений — параметр видимости не
  найден, и возвращать нечего. Со сборки 64 имя параметра читается из
  словаря определения (`ACAD_ENHANCEDBLOCK` → группа 301), а не угадывается
  по написанию имени, поэтому такой случай теперь возможен только если
  вложенный блок действительно не динамический.
* **`не найдено в новой версии`** — такого вложенного блока в новой версии
  нет, состояние вернуть некуда.
* **`записать не удалось`** — AutoCAD отказался писать свойство.
* **`запись не подтвердилась чтением`** — вызов записи прошёл, а чтение
  показало другое значение. Это значит, что состояние НЕ применилось, хотя
  отказом не выглядит. Главный признак того, что на чертеже осталось значение
  мастер-блока.
* **`Определений, в которые возвращены состояния`** — какие именно определения
  обработаны. Если нужного вам блока в этом списке нет, значит состояния для
  него не снялись, и искать надо в снимке.

С подробной печатью `(setq KG-TRACE-DETAIL t)` каждое состояние печатается
отдельно:

```
[шаг] состояние Закладная КП45302="Открыто" -> "Открыто"
[шаг] состояние Уплотнение="Скрыто" -> "Скрыто" НЕ ПРИНЯТО
```

Определения по схеме семейства (`БАЗА vВЕРСИЯ [ВАРИАНТ]`) этот шаг не
трогает: у них состояния переносятся по экземплярам, и в отчёте это строка
`Восстановлено состояний видимости`.

### Обновление одноимённых блоков по всему чертежу

Одноимённое определение получает новое содержимое из буфера не только там,
где его вставляют в модель, но и внутри чужих определений и внутри анонимных
представлений. Для этого после вставки выполняется отдельный шаг, и в отчёте
появляются строки:

```
[шаг] перепривязка ссылок на прежние имена
...
Перепривязано ссылок на прежние имена: 41
[шаг] перепривязано ссылок на прежние имена: 41
```

Если часть ссылок вернуть нельзя, потому что определение замкнулось бы само
на себя, печатается:

```
ВНИМАНИЕ: вставка "Гайка~до1.5" внутри "Гайка" оставлена как есть -- иначе
определение замкнулось бы само на себя.
Оставлены как есть (риск зациклить определение): 1
```

Это не ошибка: такие вставки остаются на старом определении, и оно не
снимется очисткой. Пришлите строку целиком — по ней видно, какое именно
определение замкнуто.

Строка `Перепривязано ссылок на прежние имена: 0` при отсутствии
предупреждений — тоже не ошибка. Переименование через `vla-put-Name` уводит
за именем ссылки AutoCAD, и возвращать бывает нечего. В прогоне на 43 парах
программа печатала список из 43 имён как «не удалось перепривязать» — это
было вводящее в заблуждение сообщение, теперь оно печатается только когда
есть пропуски из-за риска замыкания.

`RDBBRIEF` теперь называет держателей:

```
  служебных (~ИМЯ): 31
  "~Гайка~1.5" держат: Чертеж А, *U133
  "~Стойка~1.5" держат: Узел 12
```

По этим строкам видно, кто именно не даёт очистке снять старое определение.
Печатается не больше восьми определений и трёх держателей у каждого.
В файлах, прошедших прежние сборки, служебные имена имеют вид `ИМЯ~до1.5`
(например `Гайка~до1.5`); такие имена тоже узнаются и очищаются.

### На крупном чертеже: метки через 200 объектов

```
[шаг] карта ссылок: объектов в наборе 1231
[шаг] карта ссылок: пройдено 200 из 1231
[шаг] карта ссылок: пройдено 400 из 1231
...
[шаг] карта ссылок: пройдено объектов 1231 из 1231
```

### Две строки со счётчиками

```
[счёт] определений в списке: 57
[счёт] вхождений прочитано: 2
```

Первая печатается после каждого чтения таблицы блоков, вторая — после
каждого сбора вхождений. Обе должны быть в логе. Если вместо какой-то из
них `ВНИМАНИЕ: …` — интеграции это не мешает, но пришлите строку целиком.

### Строка `[счёт] определений в списке: N`

Печатается после каждого чтения таблицы блоков. Если вместо неё
`ВНИМАНИЕ: не напечаталось число определений (…, значение: …)` — интеграции
это не мешает, но пришлите строку целиком: в ней назван вызов и значение,
на котором он отказал.

### Как читать причину отказа

Сборка 57 печатает её так:

```
ВНИМАНИЕ: снимок чертежа не прочитан (шаг "сбор вхождений", неверная функция: T).
```

В скобках — **шаг, на котором случилось**, и сообщение AutoCAD. До сборки 57
там печатался последний шаг, а `KG-Trace` перезаписывает его на каждом
удачном шаге, поэтому сообщение называло место, пройденное ДО отказа, и
уводило в сторону.

### Если в логе появилось «определение … не прочитано … пропущено»

Это не отказ команды. AutoCAD не отдал свойства одного определения
(обычно анонимного представления `*U`), и сборка 56 пропускает его,
называя имя и причину. Команда идёт дальше. Отдельной строкой печатается
`Определений не прочитано и пропущено: N` и до 10 имён.

Тревожиться стоит только если среди пропущенных окажется имя нужного
вложенного определения — тогда пришлите этот список.

До сборки 56 такой отказ обрывал `RDB` (`INTEGRATE`) целиком: прогон на новом
реципиенте остановился на `ОШИБКА: неверная функция: T` с последним шагом
`чтение определения "*U87"` — уже после вставки из буфера.

### Что печатается, а что свёрнуто

По строке на объект больше не печатается. Вместо этого — счётчик и, где
нужно, первые 10 имён:

| Было | Стало |
|---|---|
| `чтение определения "…"` ×105 | `определений прочитано: 105` |
| `вложенная вставка "…"` ×83 на экземпляр | `в определении "…" вложенных вставок: 83, состояний прочитано: 3` |
| 9 строк на каждое вхождение | `вхождений прочитано: N` |
| `переименование "…"` ×105 | `освобождено имён: 105` |
| `стирание "*U…"` + причина, ×2 на каждое | `Стёрто сиротских *U: N, не удалось: M` |
| полные списки имён (111, 105, 43, 37) | счётчик + первые 10, дальше `... и ещё N` |

Всегда печатается целиком: отказы, предупреждения, `ОСТАЛИСЬ СТАРЫМИ`,
`=== Результат ===`, обе строки `=== ИТОГ … ===`.

Полный лог с `KG-TRACE` присылать не нужно: он не помещается в
сообщение, а всё нужное есть в пунктах 1–4.

## Все команды

| Основная команда | Алиасы | Когда | Что делает |
|---|---|---|---|
| `RDB` | `RepDblock`, `ПОДМЕНАБЛОКА`, `ПДБ`, `INTEGRATE` | реципиент, блок в буфере | весь прогон: замена экземпляров + очистка |
| `RDBBRIEF` | `INTBRIEF`, `ПДБКРАТКО` | реципиент, до и после | короткое состояние чертежа (10–15 строк) |
| `RDBREPORT` | `INTREPORT`, `ПДБОТЧЁТ` | реципиент, после прогона | полный отчёт последнего прогона по семьям, без шума очистки |
| `RDBERR` | `INTERR`, `ПДБОШИБКА` | реципиент, после падения | ошибка, шаг падения, переключатели |
| `RDBCOUNT` | `INTCOUNT`, `ПДБСЧЁТ` | реципиент, по желанию | по каждому определению — число вставок (длинно) |
| `RDBCLEANUP` | `INTCLEANUP`, `ПДБОЧИСТКА` | реципиент | только очистка, без интеграции |
| `RDBRECOVER` | `INTRECOVER`, `ПДБВОССТАНОВЛЕНИЕ` | реципиент, после жёсткого падения | довести до конца возврат по журналу |
| `RDBHEAL` | `INTHEAL`, `ПДБЛЕЧЕНИЕ` | реципиент, испорченный сборками до 72.4 | собрать заново паспорта представлений: вернуть имена вложенных динамических блоков |
| `RDBCHECK` | `INTEGRATECHECK`, `REPDBLOCKCHECK`, `ПДБЧЕК` | реципиент | скан без изменений: что было бы заменено |
| `RDBDIAG` | `INTDIAG`, `ПДБДИАГ` | реципиент | диагностика выбранного экземпляра и определений |
| `RDBDUMP` | `INTDUMP`, `ПДБДАМП` | реципиент | динамические свойства выбранной вставки |
| `RDBDUMPDEF` | `INTDUMPDEF`, `ПДБДАМПОПР` | реципиент | содержимое определения по имени |
| `RDBPASTETEST` | `INTPASTETEST`, `ПДБТЕСТВСТАВКИ` | реципиент | что реально приносит вставка из буфера |
| `RDBTESTBED` | `INTTESTBED`, `ПДБСТЕНД` | пустой чертёж | учебный стенд (статические блоки, динамики нет) |
| `RDBDBXTEST` | `INTDBXTEST`, `ПДБТЕСТDBX` | по запросу | проверка ObjectDBX (глубокое клонирование) |
| `RDBRENAMETEST` | `INTRENAMETEST`, `ПДБТЕСТПЕРЕИМ` | по запросу | проверка переименования и динамики |

Переключатели (задаются в командной строке реципиента):

| Переменная | По умолчанию | Смысл |
|---|---|---|
| `KG-TRACE` | `nil` | печать шагов; **выключайте после прогона** |
| `KG-TRACE-DETAIL` | `nil` | по строке на каждое определение, вложенную вставку, поле вхождения и переименование. Включать только когда нужно увидеть место падения внутри цикла |
| `KG-AUTOCLEAN` | `t` | очистка в конце `RDB` |
| `KG-CLEANUP-ERASE-U` | `t` | стирать сиротские `*U` |
| `KG-CLEANUP-DELETE` | `nil` | удалять свои определения самим (иначе их снимает PURGE) |
| `KG-CLEANUP-ASK` | `nil` | спрашивать подтверждение перед очисткой |

## Прогон на 100 экземплярах

Тот же порядок, только реципиент — рабочий чертёж со 100 вхождениями.
Учебный стенд `RDBTESTBED` для этого не годится: он создаёт статические
блоки без динамики и без вложенных определений, то есть именно те ветки,
которые чинились, на нём не исполняются.

Что добавляет большой прогон: время (обход содержимого определений идёт на
каждый экземпляр) и число сиротских `*U`. Если будет идти долго — это
нормально, но напишите, сколько заняло.

---

Приметы текущей сборки: **72.7**.

* в баннере при загрузке — `RepDblock.lsp, сборка 72.7`;
* новая команда `RDBHEAL` (`INTHEAL`, `ПДБЛЕЧЕНИЕ`) — лечение паспортов
  представлений, вернуть имена вложенных динамических блоков (см. «Что
  нового в сборке 72.4»);
* при включённом `(setq KG-TIMING t)` — строки `[время] <шаг>: N с`,
  сводка `=== ЗАМЕРЫ ВРЕМЕНИ (с) ===` с итогом `ИТОГО прогон: N` и блок
  `-- суб-замеры (накопительно) --` со строками `суб: <шаг>: N с (K выз.)`;
* при нескольких семьях — разделители `--- Семейство i из N: … ---`;
* в чтении модели — отметки `[шаг] обход вставок: N из M, handle …`
  каждые 100 вставок;
* при `KG-TIMING` — `=== ЗАМЕРЫ ВРЕМЕНИ (промежуточные, после
  семейства i из N) ===` после каждого семейства;
* в отчёте — строка `Снято старых определений семейства: N`;
* в хвосте журнала — повтор `=== ОТЧЁТ ПОСЛЕДНЕГО ПРОГОНА (повтор после
  очистки) ===`; его можно копировать, не пролистывая строки PURGE;
* команда `RDBREPORT` (`INTREPORT`, `ПДБОТЧЁТ`) — полный отчёт последнего
  прогона без служебных строк очистки;
* в списке блоков временные имена начинаются с `~` (например `~Мастер~1.5`);
* в суб-замерах — фазы шага «замена экземпляров» («замена: план
  видимости», «замена: создание экземпляра», «замена: динамические
  свойства», «замена: вложенная видимость», «замена: удаление старого»)
  и отдельное чтение модели на шагах семьи («семья: чтение модели
  (вложенные / старые / контроль)»);
* в суб-замерах 72.5 — «семья: снимок содержимого определений» (снимок
  перед шагом перепривязки), «модель: определения», «модель: вхождения»,
  «модель: вхождение -- геометрия / вложенные состояния / динамические
  свойства»; чтение модели для шага «вложенные» берёт только вхождения —
  определения этому шагу не нужны;
* в суб-замерах — разбивка переноса динамических свойств: «замена: свойства
  -- карта имён» (сбор имён одним проходом), «замена: свойства -- вход
  (работа)» (список свойств экземпляра), «замена: свойства -- чтение
  (работа)», «замена: свойства -- запись (работа)» и счётчики «замена:
  свойства -- совпало / -- записано / -- не удалось / -- попытки записи /
  -- без пары» (число вызовов);
* перед PURGE паспорта динамики перепривязываются (сборка 72.4; раньше
  деревья снимались, и это ломало имена вложенных блоков): флаг
  `KG-CLEANUP-STRIP` (по умолчанию t), в суб-замерах — «очистка:
  перепривязка паспортов динамики», при `KG-TRACE-DETAIL` — строки
  «паспорт динамики: … перепривязан»; паспорт без замены остаётся, и
  вставка называется в отчёте;
* рядом с чертежом может появиться журнал `RepDblock_journal_<имя>.txt` —
  это рабочий файл возврата; после штатного конца команды он удаляется, а
  после жёсткого падения по нему восстанавливается состояние (команда
  `RDBRECOVER` или любая следующая команда).

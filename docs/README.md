# Integration.lsp — интеграция новой итерации семейства динамических блоков

AutoLISP-реализация команды `INTEGRATE` по техническому заданию: перенести в
текущий чертёж новую версию семейства блоков, пришедшую **из буфера обмена**,
заменив все старые итерации и сохранив количество, положение и состояния
видимости экземпляров.

---

## 1. Установка и запуск в AutoCAD

```
APPLOAD  ->  Integration.lsp  ->  Load
```

или

```lisp
(load "C:/путь/Integration.lsp")
```

При загрузке печатается номер сборки — `Integration.lsp, сборка 13`. Тот же
номер повторяет `INTEGRATE` в первой строке: по нему видно, что загружен
именно новый файл.

Добавьте файл в `acaddoc.lsp` или в Startup Suite, если команды нужны в каждом
чертеже. Файл самодостаточен: временных файлов, лог-файлов и внешних
зависимостей не создаёт, весь вывод идёт в командную строку.

### Команды

| Команда | Назначение |
|---|---|
| `INTEGRATE` | основная команда: полная интеграция новой итерации |
| `INTEGRATECHECK` | диагностика без изменений: какие итерации и экземпляры семейства найдены, где они лежат |
| `INTDIAG` | пройти по всем определениям и вхождениям и назвать объект и шаг, на котором чтение ломается; чертеж не меняет |
| `INTDUMP` | показать по выбранному блоку эффективное имя, определение, вложенные блоки, параметр видимости и его состояния |
| `INTDUMPDEF` | показать состав и состояния видимости определения по имени |
| `INTPASTETEST` | диагностика вставки: какие определения реально пришли из буфера, а какие AutoCAD подставил существующими |
| `INTTESTBED` | создать в текущем чертеже тестовые блоки семейства (этап 0) |

### Порядок работы

**Основной сценарий (рекомендуется).**

1. В файле-источнике выделите мастер-блок `БАЗА(N)` — имя **без суффикса
   варианта** — и скопируйте его (`Ctrl+C`). Копировать нужно именно вхождение
   блока: вместе с ним в буфер попадают вложенные определения.
2. Откройте файл-реципиент и вставьте блок (`Ctrl+V`) в любое место —
   координаты не важны, экземпляр будет удалён.
3. Выполните `INTEGRATE` и **кликните по вставленному мастер-блоку**.
   Команда возьмёт из его имени семейство и номер новой итерации.
4. Прочитайте отчёт в командной строке. Вставленный вами экземпляр
   считается техническим и удаляется в конце — итоговое количество
   экземпляров не меняется.

**Запасной сценарий (без ручной вставки).**

На шаге 3 нажмите `Enter`, ничего не выбирая. Команда сама выполнит
техническую вставку из буфера обмена в точку `(0,0,0)`, определит имя
мастер-версии по пришедшим определениям и сама удалит технический экземпляр.
Режим удобен, но менее нагляден: вы не видите, что именно пришло из буфера.

Перед вставкой полезно выполнить `INTEGRATECHECK` — команда покажет, какие
итерации семейства уже есть в файле и где лежат экземпляры, ничего не меняя.

## 2. Как устроена программа

Файл `Integration.lsp` (3214 строк) разделён на два слоя, которые связаны
только через набор функций-адаптеров `KG_EX*` и `KG_DBGetModel`:

| Раздел | Строка | Содержание |
|---|---|---|
| 1 | 53 | утилиты: регистронезависимое сравнение, уникальные имена, распознавание служебных имён |
| 2 | 350 | парсер имён: `БАЗА vВЕРСИЯ ВАРИАНТ` и `БАЗА(ИТЕРАЦИЯ)ВАРИАНТ` |
| 3 | 612 | модель чертежа и сканирование семейства (модель, все листы, определения) |
| 4 | 774 | планирование: карта интеграции, разбор вложенных определений, план видимостей |
| 5 | 978 | валидация результата и печать отчёта |
| 6 | 1105 | контракт адаптера (описание, какие функции обязан предоставить слой БД) |
| 7 | 1132 | шаги интеграции и оркестрация `KG-Integrate_Model` |
| 8 | 1664 | исполняющий слой AutoCAD: COM/ActiveX, команды |

### Итерация — строка, а не число

Версия `1.5` — это строка: `(itoa "1.5")` и `(< "1.5" "1.1")` в AutoCAD
падают с `неверный тип аргумента: fixnump`. Поэтому порядок версий задаёт
`KG-IterKey` (части дополняются нулями до 6 разрядов) в паре с
посимвольным `KG-StrLt`, а сортировка идёт через `(sort its 'KG-IterOlder)`.

### Определение пространства экземпляра (строка 1717)

Экземпляр обязан остаться там, где лежал: в модели или на том же листе.
Группа 330 (`handle` владельца) в `entget` экземпляра есть **не во всех
файлах** — на реальном чертеже (прогон `FINDBUG`) её не оказалось ни у
одного `INSERT`, из-за чего `handent` получал `nil` и падал на каждом
вхождении: чертёж читался как пустой.

Поэтому пространство определяется картой `handle → пространство`
(`KG-BuildSpaceMap`, строка 1751): проход по таблице блоков, для модели и
каждого листа запрашивается `handle` каждого лежащего в нём объекта. Карта
строится один раз за команду. Группа 330 осталась запасным путём. Если
пространство определить не удалось, экземпляр **пропускается** с
предупреждением — молча считать его моделью нельзя.

**Разделы 1–7 не содержат ни одного обращения к AutoCAD.** Они работают с
абстрактной моделью чертежа, поэтому полностью проверены тестами на
собственном интерпретаторе AutoLISP без AutoCAD.

**Раздел 8** содержит только обращения к AutoCAD и guarded-обёрткой
`(if (not KG-TESTING) ...)` отключается при запуске тестов.

### Контракт адаптера (раздел 6)

Слой БД обязан предоставить:

```
KG_DBGetModel ()                     -> модель чертежа
KG_EXAllDefNames ()                  -> список имён определений
KG_EXDefExists (name)                -> T/nil
KG_EXRenameDef (old new)             -> T/nil
KG_EXDeleteDef (name)                -> T/nil
KG_EXPasteAtOrigin ()                -> вставить буфер в (0,0,0)
KG_EXNewInstancesSince (snapshot)    -> новые экземпляры после снимка
KG_EXInstanceHandle (handle)         -> модель экземпляра
KG_EXCreateInstance (def instmodel)  -> handle нового экземпляра
KG_EXDeleteInstance (handle)         -> T/nil
KG_EXRestoreDynProps (handle props)  -> перенести прочие динамические параметры
KG_EXSetEffectiveName (handle def)   -> T/nil
KG_EXSetNestedVisibility (h nm val)  -> T/nil
KG_EXCreateDefFromMaster (new master)-> T/nil
```

Каждая из них реализована дважды: в `Integration.lsp` (AutoCAD, раздел 8) и в
`tests/tests.lsp` (заглушка поверх фейковой БД).

## 3. Схемы именования

Программа понимает две схемы и выбирает нужную по виду имени.

**Производственная (основная): `БАЗА vВЕРСИЯ ВАРИАНТ`**

| Имя | База | Итерация | Вариант |
|---|---|---|---|
| `Комплект КП50 v1.5` | `Комплект КП50` | `1.5` | — (мастер-версия) |
| `Комплект КП50К v1.5` | `Комплект КП50К` | `1.5` | — |
| `Комплект КП50 v1.21 стойка КП45302-1` | `Комплект КП50` | `1.21` | `стойка КП45302-1` |

* версия — всегда `v` + цифры через точку: `v1.1`, `v1.5`, `v1.21`, `v2.0`;
* база может содержать что угодно, в том числе пробелы и букву `К`;
* вариант отделяется от версии пробелом и может содержать пробелы и дефисы;
* мастер-версия — имя без варианта;
* версии сравниваются по частям, поэтому `v1.21` **старше** `v1.5`;
* старой считается любая итерация, отличная от новой.

**Из технического задания: `БАЗА(ИТЕРАЦИЯ)ВАРИАНТ`**

`ABC1.01(15)Стойка` → база `ABC1.01`, итерация `15`, вариант `Стойка`.
Разбирается **последняя** закрывающая скобка, поэтому
`A(1)(2)Стойка` → база `A(1)`, итерация `2`, вариант `Стойка`.

Имена без узнаваемой версии (`Стойка КП50 контур`, `kps 714 в динамике`)
не разбираются и семейством не считаются — такие блоки команда не трогает.

## 4. Алгоритм

1. **Определить мастер.** Режим B — пользователь указывает блок без суффикса
   (`entsel`); режим A — вставка из буфера, имя определяется по пришедшим
   определениям, технический экземпляр запоминается и удаляется в конце.
2. **Разобрать имя.** Поддерживаются две схемы — см. раздел «Схемы
   именования» ниже. Ничего не зашито на конкретное семейство: база,
   итерация и вариант берутся из фактического имени.
3. **Просканировать чертёж целиком**: модель, все листы, определения блоков.
   Посторонние семейства (`ABC1.02`, `XYZ1.01`) не затрагиваются. Определения
   внешних ссылок (XREF) и анонимные определения исключаются из выборки
   сразу, без сообщений.
4. **Освободить имена до вставки.** `PASTECLIP` не переопределяет
   существующие определения — он игнорирует их и подставляет старые. Поэтому
   конфликтующие вложенные определения переименовываются в `ИМЯ~доN`
   **до** вставки, а не после. Имя самой мастер-версии освобождается
   отдельно (`KG-FreeMasterName`, строка 818): оно не входит в список
   вложенных, но если оно занято определением от прошлой неудачной попытки,
   AutoCAD отбрасывает пришедшее определение целиком. Если вставка не дала
   мастер-версию, имя возвращается на место (`KG-RestoreMasterName`,
   строка 841) **до** отката вложенных переименований.
5. **Вставить и сравнить снимки таблицы блоков**: что реально пришло, а что
   AutoCAD подставил старым. Если вложенное определение осталось старым —
   выдаётся предупреждение с именем.
6. **Спланировать**: какие варианты `БАЗА(N)ВАРИАНТ` создать, какие вложенные
   определения обновить/добавить.
7. **Заменить экземпляры** «создать новый → удалить старый», перенося
   положение, масштабы XYZ, поворот, нормаль, слой и пространство
   (модель→модель, лист→тот же лист). Handle при этом меняется — это
   отражается в отчёте.
8. **Восстановить состояния видимости** индивидуально по каждому экземпляру
   и по каждому вложенному блоку. Параметр видимости ищется эвристиками
   (`Visibility`, `Видимость`, `Видимость1`, …), конкретное имя не зашито.
   Если старого состояния в новой версии нет — устанавливается **первое
   доступное** и печатается предупреждение вида:

   ```
   Блок: ABC1.01(4)
   Вложенный блок: Стойка
   Старое состояние "D" отсутствует в новой версии. Установлено состояние "A".
   ```
9. **Перепривязать вложенные вхождения** внутри сторонних определений на
   новые определения, сохранив исходные имена.
10. **Проверить результат**: количество по вариантам, по пространствам,
    отсутствие старых имён и служебных суффиксов (`$0$`, `$1$`, `_new`,
    числовые, `копия`). Расхождения печатаются.

Старые вложенные определения **не удаляются**: они переименовываются в
`ИМЯ~доN` и сообщаются в отчёте (удаляются потом через `PURGE`). Переменная
`KG-DELETE-OLD-DEFS` (по умолчанию `nil`) разрешает удалять их сразу.

`tests/autolisp.py` — интерпретатор подмножества AutoLISP (списки, assoc,
строки, `wcmatch`, `vl-*`, локальные переменные `defun`). Числовые операторы
`< > <= >=` и `itoa` в нём **строги к типу**, как в AutoCAD: на строке они
бросают `неверный тип аргумента: fixnump`. Раньше интерпретатор сравнивал
строки как Python, и поэтому не поймал `(sort its '<)` над версиями — на
реальном чертеже это упало именно так. `sort` с предикатом «строго меньше»
тоже работает как в AutoLISP: компаратор возвращает `T`/`nil`, а не `-1/0/1`. `tests/tests.lsp` —

`tests/check_load.py` загружает `Integration.lsp` целиком (без `KG-TESTING`),
подставляя заглушки примитивов COM, и проверяет, что в разделе 8 нет вызовов
неопределённых функций.

`tests/run_space_tests.py` идёт дальше: он тоже загружает файл без
`KG-TESTING`, подставляет фейковый чертёж (модель, два листа, лист без
объекта `Layout`, определение с вложенным вхождением, внешняя ссылка) и
**исполняет** настоящие `KG-BuildSpaceMap`, `KG-SpaceOfHandle`, `KG-SpaceOf`,
`KG-HandleOf`, `KG-OwnerBlockName`, `KG-RecordNameOf`, а также
`KG-InstanceModel` на двух «трудных» вхождениях: у одного не читается
**ничего**, кроме handle, у второго читаются все свойства. Группа 330 в
фейковом `entget` отсутствует — как в реальном файле, а `InsertionPoint`
возвращается **variant'ом**, а не списком.

### Значения COM нельзя разбирать списковыми функциями

`InsertionPoint`, `AllowedValues` и `Value` приходят variant'ами. `(nth i
variant)` в AutoCAD даёт «неверный тип аргумента: consp #<variant …>» —
именно так падало чтение **каждого** вхождения на реальном чертеже. Все
значения COM разворачиваются через `KG-ListValue` (`vlax-variant-value` +
`safearray`) и `KG-PointValue`, списковые функции к ним не применяются.
Счётчики в отчёте идут через `KG-NumStr`: `(itoa nil)` — это «fixnump: nil».

Карта пространств строится проходом по таблице блоков; если он не дал ни
одного объекта, включается запасной путь `KG-BuildSpaceMapByLayouts` —
обход коллекции `Layouts` (строка 1796). На реальном чертеже основной путь
дал 0 объектов, и запасной сработал: карта на 65 объектов. Счётчик
«пространств пройдено» в сообщении при этом остаётся нулевым — сообщение
косметически неверно, на результат не влияет.

### Имя мастер-версии обязано быть свободным до вставки

На реальном чертеже команда доходила до вставки и получала
`Мастер-версия «Комплект КП50 v1.5» НЕ получена из буфера`: AutoCAD печатал
`Duplicate definition of block ... ignored` и подставлял старое определение.
`KG-ConflictCandidates` (строка 798) собирает только **вложенные** имена и в
конце сам вырезает имена семейства — имя мастер-версии через него не
освобождается, а нужно оно ровно для вставки. Поэтому освобождением имени
мастера занимается отдельная функция, и проверка «пришла ли мастер-версия»
идёт напрямую — `(KG_EXDefExists имя)` после вставки при освобождённом имени,
а не сравнением снимков таблицы блоков.

### В AutoCAD нет функций `sort` и `make-string`

Прогон сборки 9 на реальном чертеже дошёл до построения плана и упал:
`no function definition: SORT`. Функции `sort` в AutoCAD **нет** — есть
`vl-sort`, `vl-sort-i` и `acad_strlsort`. Ровно так же в отчёте оказалась
`make-string` (есть в Common Lisp, в AutoCAD её нет) — она заменена на
собственную `KG-Pad`.

Обе ошибки тесты пропускали, потому что собственный интерпретатор
(`tests/autolisp.py`) эти функции определял. Теперь:

* `sort` и `make-string` из интерпретатора **удалены** — стенд больше не
  прощает то, что не примет AutoCAD;
* добавлена проверка `tools/check_acad_funcs.py`: она разбирает файл и
  сверяет каждую голову списка и каждый символ `KG-*` со списком
  действительно существующих функций AutoCAD и с определениями самого
  файла. Проверена на контрольных образцах: подделка `sort`,
  `make-string` и `KG-PadTYPO` ловится.

### Имена освобождались ПОСЛЕ вставки — то есть никогда

`INTPASTETEST` и `INTEGRATE` на реальном чертеже показали причину, по
которой 42 вложенных определения оставались старыми. Вставка из буфера
выполняется в команде `C:INTEGRATE`, а имена освобождал
`KG-Step_PreRename` внутри `KG-Integrate_Model` — **после** вставки.
К моменту вставки имена были заняты, AutoCAD печатал «Duplicate
definition of block … ignored» и подставлял старые определения.

Теперь `C:INTEGRATE` до вставки:

1. освобождает вложенные имена (`KG-ConflictCandidates` + `KG-Step_PreRename`)
   и передаёт список через `KG-PRERENAMES`;
2. освобождает имя мастер-версии — иначе мастер не приходит, если имя
   занято определением от прошлой неудачной попытки;
3. сохраняет снимок таблицы блоков в `KG-PREDEFS`: по снимку, снятому
   после переименования, «обновить существующее» и «добавить новое»
   меняются местами (это ловят `T12.7`/`T12.7b`).

`KG-Integrate_Model` в режиме вставки свои переименования не делает —
переименовывать пришедшие определения нельзя, содержимое снова стало бы
старым. Сигнатуру функции менять нельзя: в AutoCAD недостающий
обязательный аргумент даёт «слишком мало аргументов», поэтому состояние
передаётся через `KG-PRERENAMES` и `KG-PREDEFS`.

Там же исправлен вызов `KG-FallbackMasterFromDrawing`: функция принимает
три аргумента (снимок вхождений, снимок таблицы блоков, модель), а
вызывалась с одним — команда падала с «слишком мало аргументов» ровно в
той ветке, где сообщается, что мастер-версия не пришла.

### Служебные суффиксы ищутся только в наших именах

Первый полный прогон `INTEGRATE` в AutoCAD (сборка 11) закончился без
ошибок, но напечатал «в файле остались служебные имена» и перечислил 79
позиций: `*Model_Space`, `*Paper_Space`, `*U8`, `*D3` … Это внутренние
анонимные определения AutoCAD, они есть в любом чертеже. Проверка
`(KG-IsServiceName nm)` по всем именам файла подменяла требование ТЗ
(«итоговые имена не должны содержать `$0$`, `_new`, `копия`») проверкой
всей таблицы блоков. Теперь проверяются только имена определений, которые
занимают созданные экземпляры, и анонимные исключены (`T13.36`, `T13.37`).

### Отчёт печатал 42 обновлённых определения при нуле обновлённых

Рядом с предупреждением «все 42 вложенных определения вставлены СТАРЫМИ»
отчёт печатал `Обновлено вложенных определений: 42` — он брал размер
плана, а не факт. Теперь печатается фактическое число, отдельно — сколько
осталось старыми, а в списке плана устаревшие помечены
`[ОСТАЛОСЬ СТАРЫМ]` (`T8.8`–`T8.10`).

Чтобы различать «AutoCAD подставил старое определение» и «определение
пришло из буфера», добавлен снимок **handle** определений
(`KG_EXDefHandleSnapshot` / `KG-ArrivedByHandle`): у заменённого
определения handle другой, даже если имя совпало. Сравнение только по
именам уже один раз дало ложный ответ на реальном чертеже
(`T10.20`–`T10.22`). В отчёт добавлены счётчики «Освобождено имён до
вставки» и «Пришло определений из буфера».

### Двойная вставка: 41 вложенное определение осталось старым

Прогон на реальном чертеже показал: `Освобождено имён до вставки: 0`,
41 вложенное определение «ОСТАЛОСЬ СТАРЫМ», в списке блоков одновременно
`Комплект КП50 v1.5` и `Комплект КП50 v1.5~до1.5`, а вместо одного
варианта создано два — второй мусорный, `Комплект КП50 v1.5 до1.1`.
Причины три, все в порядке действий:

1. **Вставка выполнялась дважды.** `C:INTEGRATE` сам вызывал `PASTECLIP`
   (чтобы узнать имя мастера), а затем передавал в `KG-Integrate_Model`
   флаг вставки — и тот вставлял ещё раз. Между двумя вставками
   освобождение имён успевало переименовать уже пришедшее определение.
   Теперь вставка одна: её делает `C:INTEGRATE`, а `KG-Integrate_Model`
   вызывается без флага вставки и берёт готовые списки
   (`KG-PREDEFS`, `KG-PRERENAMES`, `KG-ARRIVED`).
2. **Имена освобождались после вставки.** `PASTECLIP` не переопределяет
   существующее определение — он печатает `Duplicate definition of block
   ... ignored` и подставляет старое. Освобождение имён перенесено в
   `C:INTEGRATE` **до** `PASTECLIP`.
3. **Освобождались имена всех семейств, а откатывались не все.** До
   вставки семейство мастера из буфера неизвестно, поэтому освобождаются
   имена всех семейств чертежа; после вставки те, что буфер **не**
   принёс, возвращаются на место (`KG-Step_RollbackNotArrived`).
   «Пришло» определяется по снимку **handle**, снятому после
   переименования и до вставки: переименование handle не меняет
   (`T10.24`), а подмена определения пришедшим — меняет, поэтому
   вложенные определения, пришедшие под тем же именем, тоже видны
   (`T10.22`).

Порядок действий проверен целиком прогоном `TEST-IntegrateAsCommand`,
который повторяет `C:INTEGRATE` шаг в шаг (`T10.25`–`T10.38`): вставка
ровно один раз, ни одно вложенное не осталось старым, мусорного варианта
нет, служебных имён нет, сторонние семейства под своими именами,
технический экземпляр удалён, счётчик сохранён. Мутация — вернуть
переименование на прежнее место — этот прогон ловит.

### Вложенные, которых в новом мастере нет, возвращаются под своё имя

Раньше освобождённое и не занятое буфером определение оставалось под
служебным именем `Закладная~до8`. Теперь имя возвращается на место:
определение сохраняется (п. 8.4 ТЗ — не удалять), а итоговые имена
остаются чистыми (`T7.37`–`T7.39`, `T10.9`–`T10.10b`).

### `:vlax-false` истинно — корень всех отказов обновления

Прогон сборки 16 напечтал `Кандидатов на освобождение: 0` при чертеже из
сотни определений. Причина — чтение логических свойств COM:

```lisp
(cons "is-xref"
      (if (vl-catch-all-apply '(lambda () (vla-get-IsXRef blk))) t nil))
```

AutoCAD возвращает `:vlax-true` / `:vlax-false`, и **оба** этих символа в
условии истинны — `(if :vlax-false t nil)` даёт `T`. Значит каждое
определение чертежа получало флаг «внешняя ссылка», `KG-UserDefNames`
возвращал пустой список, и освобождать перед вставкой было нечего. Одна
строка объясняет оба предыдущих отказа: в сборке 15 осталось одно имя
(его добавлял отдельный ветвящийся код, не проходивший через этот
фильтр), в сборке 16 — ноль.

Все шесть мест, где так читались `IsXRef` и `IsDynamicBlock`, переведены
на предикат `KG-ComBool` (`T13.38`–`T13.44`).

Тесты этот баг не ловили, потому что интерпретатор превращал
`:vlax-false` в `nil`, а стенд раздела 8 возвращал `None` вместо
`:vlax-false` — оба были добрее настоящего AutoCAD. Исправлено и то и
другое: интерпретатор теперь понимает ключевые слова как в AutoCAD, стенд
возвращает `:vlax-false`, добавлены `M23`/`M24`. Мутация (вернуть
`(if … t nil)`) даёт ровно ваш симптом: `KG-UserDefNames -> nil`.

### Вариант обязан остаться динамическим

`Комплект КП50 v1.5 КП45387` создавался статическим. Причина: вариант
строился как «создать пустое определение и скопировать в него объекты
мастера», а параметры динамического блока лежат в словаре расширения
`BLOCK_RECORD` (`ACAD_ENHANCEDBLOCK`), API их не отдаёт, и при таком
копировании они не переносятся.

Решение — глубокое клонирование через ObjectDBX (`KG_EXCopyDefDeep`):
определение клонируется в невидимый документ ObjectDBX **в памяти** (без
файла на диске), там переименовывается и копируется обратно. Приём Lee Mac
(`LM:CopyBlockDefinition`), который прямо рассчитан на динамические
определения. Если ObjectDBX недоступен — запасной путь
`KG-EXCreateDefStatic` и явное предупреждение, что вариант получится
статическим (`T10.47`–`T10.52`, мутация «выключить клонирование» ловится).

Проверить на своём чертеже за пять секунд, ничего не меняя: команда
`INTDBXTEST` — выбрать блок, она создаст копию `имя~тест`, напечатает
«Копия динамическая: ДА/НЕТ» и удалит её.

### Освобождаются все имена, а не угаданный список

Кандидаты на освобождение собирались по старым версиям семейства. На
реальном чертеже это дало **одно** имя, и 41 вложенное определение не
освободилось — PASTECLIP подставил старые. Состав новой мастер-версии до
вставки неизвестен, поэтому угадывать его не нужно: освобождаются имена
**всех** пользовательских определений (кроме анонимных, листовых и внешних
ссылок), а чего буфер не принёс — возвращается под прежним именем. В отчёт
добавлена строка «Кандидатов на освобождение».

### «Обновлено вложенных: 0» при 42 «добавленных»

Прогон сборки 14 на реальном чертеже: вложенные определения пришли, но
отчёт напечатал `Обновлено вложенных определений: 0` и перечислил 42 имени в
«Добавлены новые вложенные определения» — хотя все 42 уже были в файле.
Причина — в передаче снимка:

```lisp
(setq plan (KG-BuildIntegrationMap model mastername
               (if do-paste beforedefs nil)))   ; <-- так было
```

Снимок таблицы блоков **до** вставки передавался в карту только тогда,
когда вставку делала сама `KG-Integrate_Model`. После переноса вставки в
`C:INTEGRATE` флаг стал `nil`, снимок перестал передаваться, и
классификация «обновить / добавить» пошла по таблице **после** вставки.
Теперь снимок передаётся всегда, когда он есть.

Тест `T10.28` эту поломку **не ловил**: он проверял «ни одно вложенное не
осталось старым», а при пустом плане старыми оказываться нечему. Добавлены
`T10.28b`/`T10.28c` — план обязан делить вложенные на обновляемые
(«Стойка», «Ригель») и новые («Адаптер»). Мутация (вернуть `do-paste` в
условие) на них падает.

### Отчёт различает три разных «не обновилось»

Одно число «Освобождено имён до вставки» не отвечало на вопрос, где
оборвалась цепочка. Теперь печатаются три:

| Строка отчёта | Что означает |
|---|---|
| Освобождено имён до вставки | сколько имён переименовано в `имя~до` до PASTECLIP |
| Из них занято пришедшими определениями | сколько из них буфер занял новым содержимым |
| Из них вернулось на место (буфер не принёс) | сколько откачено, потому что ничего не пришло |
| Не удалось переименовать | список имён, которые AutoCAD не дал переименовать |

`0 / 0 / 0` — имена не освобождались, PASTECLIP подставил старое.
`N / 0 / N` — освободились, но буфер ничего не принёс.

### Лишний экземпляр новой версии больше не «потеря»

`INTPASTETEST` оставлял техническую вставку в начале координат. На
следующем `INTEGRATE` она считалась экземпляром новой итерации, и отчёт
печатал `Потерь экземпляров: 1` и `Вариант "": ожидалось 1, стало 2
[РАСХОЖДЕНИЕ]`. Исправлено с двух сторон: `INTPASTETEST` удаляет свою
вставку сам, а валидация прибавляет к ожидаемому числу экземпляры,
которые уже стояли на новой итерации до замены
(`KG-ExpectedWithExisting`, `T10.42`–`T10.46`). Мутация (выключить
поправку) даёт ровно `получено 1` — ту самую цифру из лога.

### Проверка числа аргументов

`tools/check_arity.py` разбирает файл на s-выражения, собирает арность
каждого `defun` и сверяет её со всеми вызовами. В AutoLISP вызов с
неверным числом аргументов падает в момент выполнения с «слишком мало
аргументов», а синтаксис при этом корректен — так упала сборка 12
(`KG-FallbackMasterFromDrawing` с одним аргументом при трёх) и так же
едва не прошла сборка 14 (`KG-AsNum` требует два, был вызван с одним).
Сейчас: 159 определений, все вызовы с верным числом аргументов.

### Режим B: мастер вставлен руками

Если пользователь вставил блок до запуска команды, переименовывать
определения уже поздно и опасно: пришедшего ждать нечего, а
переименование оторвало бы мастер-версию от её собственных вложенных
определений. В этом режиме переименований нет и печатается предупреждение
с рекомендацией нажать Enter (`T10.39`–`T10.41`).

### Падение команды не должно оставлять переименованное определение

Прогон сборки 9 освободил имя мастер-версии (`Комплект КП50 v1.5` →
`Комплект КП50 v1.5~до1.5`), затем упал на `SORT` — и откат не сработал:
в списке блоков осталось определение с временным именем. Обработчик ошибок
`KG-ErrorRestore` теперь возвращает имя обратно, но **только если оно
свободно**: если его уже заняло пришедшее из буфера определение, трогать
его нельзя — в этом случае печатается сообщение, что определение осталось
под временным именем. Проверено `M19`–`M22`.

### Подробные шаги не должны переполнять командную строку

AutoCAD показывает только хвост сообщения, поэтому на чертеже с десятками
вхождений пометки каждого прочитанного поля выталкивали из видимой области
итоговый отчёт. Метка шага теперь печатается только при `(setq KG-TRACE t)`
(по умолчанию `nil`); запоминается она всегда, и обработчик ошибок по-прежнему
называет объект, на котором команда упала. Если `KG-TRACE` включён,
`INTEGRATE` печатает об этом отдельной строкой — чтобы многословный вывод
не выглядел как сбой. Отключение: `(setq KG-TRACE nil)`.

### Чтение экземпляра не должно быть «всё или ничего» (строка 2161)

`KG-InstanceModel` читает каждое поле отдельно, со своим запасным
значением и меткой `KG-Trace` («вхождение 7B33: слой»). Раньше одно
нечитаемое свойство обрывало чтение **всех** вхождений, и чертёж
оказывался «пустым» — `вхождений прочитано: 0, пропущено из-за ошибок: 5`.
Числовые поля приводятся через `KG-AsNum`, строковые — через `KG-AsString`:
`nil` в `itoa`/`rtos`/арифметике даёт «неверный тип аргумента: fixnump: nil».
`KG-CollectInstances` печатает **причину** по каждому пропущенному
вхождению, а не только факт.

### Три строки отчёта, которых не хватало (сборка 18)

Прогон сборки 17 на реальном чертеже впервые обновил вложенные определения
(`Обновлено вложенных определений: 40`, потерь нет), но оставил три вопроса,
на которые отчёт ответить не мог.

**1. «Восстановлено состояний видимости: 0» выглядело как потерянное
состояние.** На самом деле этот счётчик считает только состояния *вложенных*
блоков. Состояние самого верхнего вхождения переносится отдельно —
`KG_EXRestoreDynProps` — и его результат выбрасывался:

```lisp
(KG_EXRestoreDynProps nh (KG-CdrCI "dyn-props" inst))   ; было
```

Теперь результат складывается в `dyn-restored` и печатается отдельной
строкой `Перенесено свойств самого блока`. «Восстановлено состояний
видимости: 0» при ненулевой второй строке — это нормально: у вложенных
блоков мастера своих состояний нет, всё состояние живёт в верхнем
вхождении.

**2. «ObjectDBX недоступен» без причины.** `KG-ObjectDbx` возвращал `nil`
из нескольких ветвей, и по отчёту было нельзя понять, на каком ProgID и на
каком способе произошёл отказ. Теперь:

- пробуются **оба** ProgID — `ObjectDBX.AxDbDocument.<версия>` и общий
  `ObjectDBX.AxDbDocument`;
- каждый пробуют **двумя** способами — `vla-GetInterfaceObject` и
  `vlax-create-object`;
- каждая неудача пишется в `KG-DBX-ERR` вместе с текстом ошибки, и этот
  список печатается в предупреждении и в `INTDBXTEST`.

То есть вместо «ObjectDBX недоступен» пользователь получает до четырёх
строк вида `ObjectDBX.AxDbDocument.25 / GetInterfaceObject: <текст ошибки>`.
Функции вынесены из раздела 8 в раздел 4, чтобы их можно было проверить
тестами (T18.1–T18.15).

**3. Судьба мастер-версии не печаталась.** `PASTECLIP` молча игнорирует
конфликтующее определение и оставляет старое — тогда вся интеграция идёт от
устаревшего мастера, а по «Пришло определений: N» этого не видно. Функция
`KG-MasterState` различает три исхода и печатает их строкой
`Мастер-версия: …`:

| исход | строка отчёта |
|---|---|
| имени не было в чертеже | пришла из буфера как новое определение |
| имя было, определение пришло | перезаписана из буфера (имя уже было в чертеже) |
| имя было, буфер его не принёс | ОСТАЛАСЬ СТАРОЙ + отдельное ВНИМАНИЕ |

На чертеже из лога сборки 17 `Комплект КП50 v1.51` не входил в 47
кандидатов на освобождение, значит имени в чертеже не было — определение
пришло из буфера новым. Теперь это утверждение печатается, а не выводится
по косвенным признакам.

### Сборка 19: «неверная функция: #<SUBR … -lambda->»

Прогон сборки 18 на реальном чертеже:

```
[шаг] замена экземпляров и перенос состояний видимости
ОШИБКА: неверная функция: #<SUBR @00000220c22f5a48 -lambda->
```

Причина — правка счётчика `dyn-restored` из сборки 18:

```lisp
(KG-Safe (lambda () (KG_EXRestoreDynProps nh ...)) 0)   ; лямбда БЕЗ кавычки
```

`vl-catch-all-apply` принимает **имя функции** или **квотированную** лямбду.
Вычисленная `(lambda () …)` превращается в SUBR, и перехватчик его отвергает.
Команда падала до замены экземпляров, поэтому старые блоки оставались на
месте.

Квотированная лямбда здесь не подходит по другой причине: в тестовом
интерпретаторе она не видит локальные `nh` и `inst` (там лексические
области видимости, в AutoCAD — динамические). Расхождение сред, которое
невозможно удовлетворить одной формой вызова, поэтому вызов **прямой**:

```lisp
(KG_EXRestoreDynProps nh (KG-CdrCI "dyn-props" inst))
```

Сама `KG_EXRestoreDynProps` внутри полностью под перехватом, обёртка ей не
нужна. Чтобы ошибка не повторилась, в `tools/check_acad_funcs.py` добавлено
правило: вычисленная лямбда в `vl-catch-all-apply` или `KG-Safe` — провал
проверки. Мутационно подтверждено: возврат вычисленной лямбды даёт
`ВЫЧИСЛЕННАЯ ЛЯМБДА В ПЕРЕХВАТЕ … KG-SAFE`.

**Правило для всех последующих правок:** в `KG-Safe` и
`vl-catch-all-apply` лямбда передаётся только квотированной, и только если
ей не нужны локальные переменные вызывающей функции. Нужны локальные —
вызов прямой.

### Сборка 20: почему «Причина: скопировать определение не удалось»

### Сборка 22: корень проблемы со статическим вариантом

Проба `INTRENAMETEST` на реальном чертеже: переименование динамику
**сохраняет** (`Комплект КП50 v1.2 КП45387` и `Комплект КП50 v1.51`, оба
раза «ДА» до, после и после возврата). Запасной путь без ObjectDBX
применим.

Но корень оказался проще и был в самом коде:

```lisp
(setq r (KG-DBX-Try "копирование в документ ObjectDBX (CopyObjects)"
          '(lambda () (vlax-invoke (KG-Doc) 'CopyObjects (list def) dbc))))
(if r ...)          ; <-- всегда ложно
```

`Document.CopyObjects` и `Database.CopyObjects` — методы **без возвращаемого
значения**, `vlax-invoke` от них даёт `nil`. Условие `(if r …)` не
выполнялось никогда, поэтому копирование обрывалось сразу после первого
шага: без ошибки (вызов прошёл) и без результата (`KG-DBX-ERR` пуст). Ровно
те два признака, которые видел пользователь: «ObjectDBX доступен» и
«причина не сообщена».

Проверять нужно не возвращаемое значение, а **последствие** — появилось ли
определение в целевой таблице блоков. Так и сделано: после первого
`CopyObjects` читается `vla-Item dbc srcname`, после переименования —
`vla-Item dbc newname`, после второго — `KG_EXDefExists`.

Тест M25–M28 (`tests/run_space_tests.py`): фейковый документ ObjectDBX, у
которого `CopyObjects` намеренно **без `return`**. Мутационная проверка:
возврат условия `(if r …)` даёт `FAIL M25/M26/M27`, причём M26 показывает
ровно ту картину, что видел пользователь. Прогон идёт отдельным
интерпретатором — M-серия переопределяет `KG_EXDefExists` заглушкой.

Там же исправлено чтение динамики у экземпляров: `IsDynamicBlock`
сравнивался с `:vlax-true` напрямую, теперь через `KG-ComBool` — тот же
класс ошибки, что и `:vlax-false` в `IsXRef`.

### INTCLEANUP: почему PURGE не берёт «…~до»

Прогон сборки 22 на реальном чертеже: вариант `Комплект КП50 v1.51 КП45387`
создан динамическим, предупреждения нет. Осталась очистка — `PURGE` не
удаляет определения `Kp45302-1~до` и подобные.

Причина в порядке, а не в AutoCAD. Старый вариант семейства
(`Комплект КП50 v1.1`) сам больше никем не используется, но **содержит**
вхождения определений `…~до`: когда определения переименовывались, ссылки
внутри него пошли за новыми именами. Пока старый вариант не удалён, каждое
`…~до` считается использованным.

`INTCLEANUP`:

1. `KG-EXRefCounts` — один проход по всем определениям, включая содержимое
   других определений, и подсчёт вхождений по эффективному имени;
2. в кандидаты попадают определения без ссылок, у которых имя содержит
   `~до` **или** разбирается схемой `БАЗА vВЕРСИЯ [ВАРИАНТ]`;
3. новейшая итерация каждого семейства защищена даже при нуле ссылок —
   `KG-CleanupKeepNewest`;
4. список печатается, спрашивается подтверждение, удаление идёт в
   несколько проходов: за проход освобождается то, на что ссылок не
   осталось, поэтому сначала уходят старые варианты, затем `…~до`;
5. что удалить не удалось — печатается отдельным списком.

Ключ защиты — **семейство и вариант**, а не одно семейство: `Комплект КП50
v1.51` и `Комплект КП50 v1.51 КП45387` — одна семья и одна итерация, но два
разных определения, и защищать надо оба. Мутационная проверка: ключ только
по семейству даёт `FAIL T17.6` и `FAIL T17.7`.

Автоматически ничего не удаляется — это отдельная команда, которую
пользователь запускает сам.

### «Прочитано свойств у старых экземпляров: 0»

Счётчик из сборки 22 показал, что состояния видимости не переносятся не
потому, что их некуда записать, а потому, что они не читаются. Причина —
в `KG-GetDynamicProperties`:

```lisp
(vlax-property-available-p obj 'GetDynamicBlockProperties)   ; всегда nil
```

`vlax-property-available-p` проверяет **свойства**, а
`GetDynamicBlockProperties` — **метод**. Проверка всегда возвращала `nil`,
условие не выполнялось, и у каждого экземпляра читался пустой список.
Правильной была бы `vlax-method-applicable-p`, но предварительная проверка
убрана вовсе: метод вызывается сразу под перехватом, и у статического блока
он просто отказывает.

Это та же семья ошибок, что `:vlax-false` в `IsXRef` и проверка результата
void-метода `CopyObjects`: код доверяет вспомогательному вызову, который в
реальном AutoCAD ведёт себя не так, как в тестовом интерпретаторе.

### 0xC0000005 на проходе 2: удаление динамического определения

Прогон на чертеже со 100 заменёнными экземплярами:

    [шаг] очистка: проход 1
    [шаг] очистка: проход 2; ошибка: Возникло исключение: 0xC0000005

Ключевое — обрыв **до первой метки удаления** на втором проходе. Значит,
падает не само удаление, а обход таблицы блоков, который идёт сразу после
него. Проход 1 к этому моменту уже удалил определения, в том числе
`Комплект КП50 v1.5 стойка КП45302-1` — динамическое определение, у
которого в чертеже 281 анонимное представление.

Та же картина, что и с переименованием `A$C…`: повреждение происходит в
одном месте, а нарушение доступа всплывает на следующей операции с базой.

Решение — убрать `vla-Delete` из очистки совсем. Собственное удаление
вынесено под переключатель `KG-CLEANUP-DELETE`, по умолчанию `nil`:
определения снимает только PURGE, своим механизмом и проверенным на
реальном чертеже. Теряется только точечность — PURGE чистит всю таблицу
блоков, — а те же `…~до` он убирает, что подтверждено прогонами.

Заодно обход таблицы блоков в `KG-EXRefHolders` укреплён: `entget` вызывается
под `KG-Safe` и проверяется на nil, потому что после удалений в обходе
попадаются стёртые объекты.

### Состояния вложенных блоков не восстанавливались никогда

Сложный файл, 100 экземпляров: интеграция прошла полностью — заменено 100,
вариант `стойка КП45302-1` сохранён (`ожидалось 100, стало 100 [OK]`),
прочитано и перенесено по 200 свойств, потерь 0. Но

    Восстановлено состояний видимости: 0

И это не особенность большого чертежа: ноль был **во всех прогонах**,
включая малый тестовый файл, где `Прочитано свойств у старых экземпляров:
4`. Читатель состояний вложенных блоков не работал ни разу.

    (defun KG-InstanceNestedVisibility (obj / out nm v)
      (vl-catch-all-apply
        '(lambda ()
           (vlax-for sub obj        <-- вставка не коллекция своих
             ...                       вложенных объектов

`AcDbBlockReference` не перечисляет содержимое своего определения:
`vlax-for` по вставке не даёт ничего, исключение глотал
`vl-catch-all-apply`, функция молча возвращала nil. Список `nested-vis`
был пуст у каждого экземпляра, поэтому `KG-PlanNestedVisibility` не
планировал ничего и счётчик стоял на нуле.

Где состояния на самом деле: у экземпляра динамического блока с
изменёнными свойствами вставка указывает на анонимное `*U133`, а не на
родительское определение. Вложенные вставки с их состояниями лежат внутри
`*U133`. Читатель переписан: имя берётся из группы 2, и если оно анонимное
(`KG-IsAnonDynName`), определение обходится через
`tblobjname`/`entnext`/`entget`, а каждая вложенная вставка читается
отдельным объектом. `vlax-for` по содержимому `*U` не используется —
именно он давал 0xC0000005 в `KG-EXRefCounts`.

Если имя вставки не анонимное, свойства экземпляра не меняли и
восстанавливать нечего — функция возвращает nil, и это правильно.

### 0xC0000005 на большом чертеже: переименование определений из внешней ссылки

Сложный файл, 1231 вхождение, шаг освобождения имён:

### Номер итерации: одна цифра — это десятки

Правило пользователя: итерации пишутся `21`, `2` (это 20), `51`, `5`
(это 50). Круглый номер пишется без нуля на конце. Порядок: 20 < 21 <
50 < 51.

`KG-IterKey` этого не знал и сравнивал части как числа:

    (KG-IterKey "1.5")  ->  ".000001.000005"
    (KG-IterKey "1.21") ->  ".000001.000021"

то есть `v1.5` (итерация 50) оказывалась **старше** `v1.21` (итерация 21),
потому что 5 < 21. Хуже того, это было закреплено тестами T13.10, T13.13,
T18.1, T18.4, T18.13 и T17.8 — шесть проверок утверждали обратное
пользовательскому правилу, и все шесть зелёные.

Теперь одноразрядная часть после точки умножается на 10; первой части
(номер версии) правило не касается:

    (KG-IterKey "1.5")  ->  ".000001.000050"
    (KG-IterKey "1.2")  ->  ".000001.000020"

Порядок итераций в T18.13 стал `1.1 1.21 1.5 2.0` — 10, 21, 50, затем
вторая версия. `KG-CleanupKeepNewest` для пары `v1.21`/`v1.5` теперь
защищает `v1.5` (T17.8).

Побочное следствие, которое надо держать в голове: `v1.5` и `v1.50` — одна
и та же итерация 50, `KG-IterEq` их уравнивает (T13.13).

Мутационная проверка: убрать `(* i 10)` — падают 8 тестов.

`*U` и свободно лежащие `~до`, второй — то, что открылось за ними, третий
добил хвост (`Kp45491 параметрический~до`, `kps 714~до`, `kps 920~до`).

Порядок «сначала своё, потом PURGE» оправдался: `Комплект КП50 v1.1` и
`v1.2 КП45387` ушли нашим точечным удалением, и только после этого
сиротами стали `*U51…`, которые держали основную массу `~до`.

### «Неизвестная команда INTCLEANUP» и лишний вопрос

В том же логе после каждого прохода PURGE печаталось

    Неизвестная команда "INTCLEANUP". Для вызова справки нажмите F1.

Причина — пустая строка в конце последовательности:

    (command "_.-PURGE" "_B" "*" "_N" "")

После `_N` PURGE завершается сам, лишний ввод не потребляется и уходит в
командную строку. Пустой Enter там означает «повтори последнюю команду», а
последняя — `INTCLEANUP`, которая уже выполняется. Отсюда сообщение, по
разу на каждый из трёх проходов. Пустая строка убрана.

Запрос подтверждения убран совсем: команда снимает только то, что нигде не
вставлено, спрашивать не о чём. `INTCLEANUP` теперь молчит и делает всё
сам. Вернуть вопрос можно переключателем:

    (setq KG-CLEANUP-ASK t)

### INTCLEANUP: один вопрос, по умолчанию Да, и ключевые слова PURGE

Прогон сборки 29 отработал корректно, но ничего не сделал: на оба вопроса
пользователь нажал Enter, а значением по умолчанию было `<Нет>`. Команда
показала 9 своих определений без ссылок и 4 сиротских `*U` — и остановилась.

Два отдельных подтверждения здесь только мешают: шаг «снять сиротские
`*U`» без шага «снять наши определения» бессмыслен, и наоборот. Оставили
один вопрос, `<Да>` по умолчанию, и перед ним показываем оба списка.
Отмена — явным `Н`.

Заодно нашлась настоящая ошибка в вызове PURGE:

    (command "_.-PURGE" "B" "*" "N" "")

У пользователя AutoCAD русский, и на подсказке «Тип объектов» он ждёт `Б`,
а не `B`. Ключевые слова в командах AutoCAD принимают английский вариант
только с подчёркиванием, поэтому правильно

    (command "_.-PURGE" "_B" "*" "_N" "")

Проходов три, а не два: свой точечный проход снимает `Комплект КП50 v1.1`
и `v1.2 КП45387`, после чего сиротами становятся `*U51…`, а уже за ними
открываются вложенные `…~до`. Запас на вложенность цепочки.

Порядок: сначала своё (если PURGE не отработает, своё уже снято), потом
PURGE, потом пересчёт и отчёт об остатке с именами держателей.

### `*U133` в кандидатах: почему программа больше не удаляет анонимные

Сборка 28 отработала без падения — обход `tblnext`/`entnext`/`entget`
оказался надёжным, карта ссылок построилась. Но в список на удаление
попали `*U53`, `*U120`, `*U133`, `*U134`.

`*U133` и `*U134` — это анонимные представления **живых** экземпляров
`Комплект КП50 v1.51` и `Комплект КП50 v1.51 КП45387`. У экземпляра
динамического блока с изменёнными свойствами вставка называется `*U133`, а
не именем родителя; если такое определение удалить, экземпляр теряет
динамику.

Отличить сироту от живого можно только по эффективному имени — то есть
через то самое COM-чтение, которое на этом чертеже даёт 0xC0000005.
Значит, надёжного критерия у программы нет. Вывод: **анонимные определения
программа не удаляет вообще**, ни при каком числе ссылок. Ветка `*U` из
сборки 28 убрана, T17.17 это фиксирует (мутационная проверка: вернуть
ветку — тест падает).

Вместо удаления — разделение ответственности:

1. Свои определения (`…~до` и старые итерации семейства) без ссылок
   программа удаляет сама, многопроходно, с пересчётом карты.
2. Сиротские `*U` она только **показывает** (`KG-CleanupOrphans`) и
   предлагает запустить `_.-PURGE` по блокам **два прохода** — ровно то,
   что вручную сработало у пользователя. Первый проход снимает `*U`,
   второй — освобождённые ими вложенные определения. PURGE живое
   представление не тронет: это собственный механизм AutoCAD.

Запрос подтверждения при этом два: сначала на свои определения, отдельно —
на PURGE. PURGE чистит всю таблицу блоков, а не только наше семейство, и
молча делать это за пользователя нельзя.

### 0xC0000005: правильный диагноз — COM-обход определений, а не `Name`

Сборка 27 с метками `KG-Mark` показала, что падение происходит на **первом**
шаге:

    [шаг] очистка: ссылки по эффективным именам; ошибка: Возникло исключение:
    0xC0000005 (Нарушение доступа)

То есть в `KG-EXRefCounts` — функции, которая живёт в файле со сборки 23 и
в сборке 25 отработала нормально. Значит, вывод сборки 26 («виноват
`vla-get-Name` у вставки») был неверным: в сборке 26 меток не было, обрыв
после заголовка выглядел так же, и я приписал его соседнему новому вызову.

Разницу даёт сравнение логов. В прогоне сборки 25 чертёж был предварительно
очищен ручным PURGE, и во второй таблице блоков **нет** `*U47`, `*U51`,
`*U52`, `*U53`, `*U55`, `*U56` — ровно тех сиротских анонимных
представлений, о которых шла речь. `KG-EXRefCounts` отработал. В прогонах
сборок 26 и 27 эти `*U` на месте («Кандидатов на освобождение: 47» против
44) — и та же функция падает.

Вывод: падает сам COM-обход — `vlax-for` по содержимому определения блока с
чтением `EffectiveName`/`Name` у вложенной вставки. На сиротских `*U` это
нарушение доступа, которое `vl-catch-all-apply` не ловит.

Решение — убрать COM из подсчёта ссылок целиком. Осталась одна функция
`KG-EXRefHolders`, которая идёт по таблице блоков штатными средствами:

    tblnext "BLOCK" -> tblobjname -> entnext -> entget

и собирает карту «имя -> список определений, внутри которых есть его
вставка». Число ссылок — длина списка; это делает `KG-CleanupCounts`
(раздел 1-7, покрыт T17.21–T17.22). Внешние ссылки отсекаются по наличию
группы 1 в записи таблицы блоков.

Единственный COM-вызов, оставшийся в пути очистки, — `KG_EXDeleteDef`
(`vla-Item` + `vla-Delete`). Он проверен на реальном чертеже: в сборке 25
так удалены три определения.

Цена решения: имя берётся из группы 2, то есть фактическое. У анонимной
вставки динамического блока там `*U77`, а не имя родителя, поэтому родитель
получит ноль ссылок. Это осознанно: удалить родителя AutoCAD всё равно не
даст, пока живо его представление, а многопроходный цикл сначала убирает
сиротские `*U`, и на следующем проходе родитель освобождается.

Мутационная проверка: если убрать проверку числа ссылок у `*U`, падает
T17.18 — тест ловит удаление представления работающего экземпляра.

### Сборка 26 упала с 0xC0000005: свойство Name у вставки читать нельзя

`INTCLEANUP` сборки 26 завершился так:

    === INTCLEANUP: очистка определений прошлой интеграции ===; ошибка: Возникло
    исключение: 0xC0000005 (Нарушение доступа)

Падение — между заголовком и первой содержательной строкой, то есть внутри
`KG-EXActualRefCounts`, единственного нового COM-вызова в этом окне. Он
читал имя вставки как свойство:

    (KG-Safe '(lambda () (KG-AsString (vla-get-Name e))) nil)

Показательно, что во всём файле `vla-get-Name` до этого вызывался только у
определений блоков (`blk`) и слоёв (`lay`) — ни разу у вставки. А
`KG-EffectiveNameOf`, у которой `vla-get-Name` стоит запасным вариантом, на
динамических блоках до этой ветки не доходит: `EffectiveName` отвечает
сразу.

Нарушение доступа `vl-catch-all-apply` не ловит — это не ошибка LISP, а
падение самого AutoCAD. Оборачивать бесполезно, вызов надо убирать.

Файл уже знал, как читать имя вставки безопасно: `KG-InstanceModel` берёт
его из DXF-группы 2 через `entget`. `KG-EXActualRefCounts` переписан на
этот способ — `vlax-vla-object->ename` (уже применяется в
`KG-EffectiveNameOf`) плюс `entget`, без единого COM-свойства вставки.

Заодно из `KG-IsAnonDynName` убран `KG-StrInterCI` (он строит замыкание
`vl-some` на каждый символ) — заменён на `KG-StrContains "0123456789"`.

В `INTCLEANUP` добавлены метки `KG-Mark` на каждый шаг. Если команда снова
упадёт, после `(setq KG-TRACE t)` последняя метка назовёт шаг.

### INTCLEANUP: кто на самом деле держит `…~до` — сиротские `*U`

Прогон сборки 25 на реальном чертеже: многопроходность сработала, но ушли
только `_Oblique~до`, `Комплект КП50 v1.2 КП45387`, `Комплект КП50 v1.1`.
`Kp45302-1 невидимый~до` и прочие остались, повторный PURGE не помог.

Ключ к разгадке в самом отчёте: не ушло **ни одно** определение, которое
лежит внутри динамического блока. Ушёл только `_Oblique` — обычный
статический блок выноски.

Держат их анонимные представления динамических блоков. Когда экземпляр
динамического блока вставлен с изменёнными свойствами, AutoCAD создаёт
`*U52` — копию определения с зафиксированными значениями. Внутри этой
копии лежат вставки вложенных блоков. Когда экземпляр заменён и удалён,
`*U52` остаётся в таблице блоков сиротой — и продолжает ссылаться на
`Kp45302-1 невидимый`, который мы к тому времени уже переименовали в
`Kp45302-1 невидимый~до`. Переименование не рвёт ссылку: она указывает на
тот же block record.

Отбор кандидатов начинался со строки

    (not (KG-IsAnonymousName nm))

и отбрасывал всё, что начинается со `*`. Значит, сиротское `*U52` не
попадало в список никогда, цепочка не размыкалась, и ни один последующий
проход ничего не освобождал.

Теперь анонимные представления динамических блоков (`*U` и только цифры —
`KG-IsAnonDynName`) в отбор включены. Проверка для них идёт по
**фактическому** имени вставки (группа 2, `KG-EXActualRefCounts`), а не по
эффективному: живое `*U133` вставлено экземпляром именно под именем
`*U133`, поэтому живые представления защищены, а сироты — нет.
`*Model_Space`, `*Paper_Space*`, `*D…`, `*X…` под правило не попадают.

Если что-то всё же не удалилось, команда теперь печатает держателя:

    Не удалено, ссылки остались: 2
      Kp45302-1 невидимый~до -- держит: *U52, *U55

Мутационная проверка: если убрать проверку фактических ссылок и удалять
любое `*U`, падает T17.18 («живое *U не кандидат») — то есть тест ловит
именно удаление представления работающего экземпляра.

### INTCLEANUP: ссылки надо пересчитывать каждый проход

Прогон сборки 24 на реальном чертеже: состояния видимости перенеслись
(`Прочитано свойств у старых экземпляров: 4`, `Перенесено свойств самого
блока: 4`), а `INTCLEANUP` удалил только три определения — `_Oblique~до`,
`Комплект КП50 v1.2 КП45387`, `Комплект КП50 v1.1`. Остальные `…~до`
остались.

Причина: список кандидатов строился **один раз**, до первого удаления.
`Kp45302-1 невидимый~до` держал на себе старый вариант `Комплект КП50
v1.1`: пока тот не удалён, вложение считается использованным и в кандидаты
не попадает. После удаления варианта оно освобождается — но подсчёт уже
сделан.

Теперь `KG-EXRefCounts` вызывается в каждом проходе (до восьми), кандидаты
пересчитываются, и за проход уходит всё, что освободилось. Логика отбора
вынесена в `KG-CleanupCandidates` (раздел 4) и покрыта T17.11–T17.15.

### Сборка 37: `PURGE` не снимает сиротские `*U` — их стирает программа

Прогон сборки 36 на реальном чертеже (100 заменённых экземпляров) дошёл до
конца без падения, но очистка не закончила работу:

```
Удалено: 110 блоки.      <- первый проход PURGE
Удалено: 12 блоки.       <- второй
Не найдены несвязанные блоки.
[шаг] очистка: контроль после PURGE
Осталось своих без ссылок: 6, сиротских *U: 180
  kps 715 в динамике~до -- держит: (прямых вставок нет, держит представление *U)
  kps 920~до            -- держит: (прямых вставок нет, держит представление *U)
  ...
```

Первый проход `PURGE` снял 110 определений, **в том числе** несколько `*U` —
значит, `PURGE` анонимные представления в принципе снимает. Но 180 сиротских
`*U` остались, и вместе с ними остались шесть старых вложенных определений
`…~до`. Причина в порядке и в области видимости `PURGE`:

* `PURGE` не заглядывает внутрь анонимного представления. Для него
  `kps 920~до` выглядит использованным (на него есть вставка внутри `*U…`),
  поэтому определение он не снимает;
* само `*U` при этом не снимается, потому что `PURGE` снимает анонимное
  представление вместе с родительским динамическим блоком, а родитель уже
  ушёл в первом проходе.

Замкнутый круг разрывается только стиранием `*U` своими силами. Добавлено:

* `KG_DefEntNames` — имена вставок внутри определения (обход через
  `tblobjname` + `entnext` + `entget`, без COM);
* `KG-OrphanContents` — карта «сирота → что внутри», она же объяснение в
  отчёте, какие определения держат сироты;
* `KG_EXEraseAnonDef` — `ENTD` по записи таблицы блоков, с проверкой, что
  определение действительно исчезло;
* `KG-CleanupEraseAllowed` — решение стирать (переключатель, наличие сирот,
  отсутствие определений из внешней ссылки);
* `KG-CLEANUP-ERASE-U` (по умолчанию `t`) — переключатель;
* `KG_HasMInsert` — защита: `MINSERT` тоже держит определение, а в подсчёт
  ссылок он не входит.

Стирание идёт до `PURGE`, несколькими проходами: внутри одного `*U` может
лежать другое `*U`, и оно становится сиротой только после стирания
внешнего. Проход повторяется, только если предыдущий что-то стёр.

### Состояния вложенных блоков не восстанавливались: писали туда же, откуда читали

Счётчик `Восстановлено состояний видимости: 0` объяснялся дважды. Первая
причина (чтение) устранена в сборке 35: `KG-InstanceNestedVisibility`
обошла анонимное представление вместо `(vlax-for sub obj)` по вставке.

Вторая причина оказалась симметричной: **`KG_EXSetNestedVisibility`
использовал тот же неработающий приём.**

```lisp
(vlax-for sub obj ...)   ; obj -- вставка, а не её содержимое
```

Цикл не выполнялся ни разу, функция возвращала `nil`, и на каждый экземпляр
печаталось «ОШИБКА: состояние видимости … не установлено». Тесты этого не
ловли: заглушка в `tests/tests.lsp` отвечала своим значением (`done`),
совпадающим по смыслу с успехом, поэтому ветки обработки ответа не
исполнялись никогда.

Сборка 37:

* запись идёт через `KG-DefInsertByName` — поиск вложенной вставки по
  эффективному имени внутри анонимного представления `*U`, куда вставка
  указывает после записи динамических свойств верхнего блока;
* если представления нет (вставка смотрит на общее определение варианта),
  состояние **не** записывается: определение общее для всех экземпляров, а
  состояние нужно одному. Случай считается отдельно (`vis-noanon`) и
  попадает в предупреждения;
* «не найдено» на первом проходе не приговор: установка состояния одного
  вложенного блока пересоздаёт представление экземпляра, поэтому такие пары
  уходят во второй проход;
* заглушка в тестах приведена к контракту настоящего адаптера:
  `T` / `nil` / `"НЕ НАЙДЕН"` / `"НЕТ ПРЕДСТАВЛЕНИЯ"`;
* в отчёте добавлены строки, по которым ноль видно насквозь:
  `Прочитано состояний вложенных блоков`, `Вложенных блоков не найдено в
  новой версии`, `Экземпляров без анонимного представления`.

**Мутационная проверка** (каждая мутация — отдельный прогон, затем откат):

| Мутация | Провалов |
|---|---|
| ветка успеха `((= r t) nil)` вместо счётчиков | 6 |
| отказ от второго прохода по «НЕ НАЙДЕН» | 1 (T19.15) |
| `KG-CleanupEraseAllowed → t` | 3 (T19.18–T19.20) |
| `entdel` в `KG_EXEraseAnonDef` не выполняется | 1 (T19.4) |
| обход `KG_DefEntNames` не смотрит на `INSERT` | 2 (T19.1, T19.2) |

**Что мутациями не проверяется.** Тело `KG_EXSetNestedVisibility` в тестах
заменено заглушкой (она живёт в исполняющем разделе 8, который стенд не
грузит), поэтому сама строка поиска вложенной вставки внутри `*U` не
исполнена — проверен только приём обхода (`KG_DefEntNames`, тот же
`tblobjname` + `entnext` + `entget`) и обработка ответов.
*Уточнение сборки 40:* `KG-DefInsertByName` из этого абзаца убрана — она
перенесена выше `(if (not KG-TESTING)` и теперь исполняется в стенде
настоящей (T19.41, T19.42). Именно её непроверенность и позволила сборке 39
уйти на диск с невызванной `KG-NestedKeyMatch`. Строка `"НЕТ ПРЕДСТАВЛЕНИЯ"` приходит из заглушки, а не из
настоящего кода: мутация этой ветки в реальном коде тестами не ловится.
`KG-CleanupRun` целиком — тоже только AutoCAD. Первые строки
`Стёрто сиротских *U: N` на реальном чертеже и есть проверка этих мест.

### `KG-Safe` принимает только лямбду: список-вызов молча не выполняется

`vl-catch-all-apply` трактует первый аргумент как **функцию**. Поэтому

```lisp
(KG-Safe (list 'entdel e) nil)   ; попытка вызвать список -> ошибка -> nil
(KG-Safe '(entdel e) nil)        ; то же самое
```

не вызывают `entdel` вообще: `KG-Safe` получает ошибку перехвата и
возвращает запасное значение. Стирание `*U` в первой редакции сборки 37
отвечало `nil` при живом `entdel`, и только поддельная таблица блоков в
тестах это показала — на чертеже выглядело бы как «не стёрлось».

Правильно — вызывать `vl-catch-all-apply` напрямую, двумя аргументами. Для
этого добавлена `KG-Call`:

```lisp
(defun KG-Call (fn args def / r)
  (setq r (vl-catch-all-apply fn args))
  (if (KG-IsErr r) def r)
)
```

`KG-Safe` остаётся для лямбд `'(lambda () ...)`: они нужны там, где вызов
должен видеть локальные переменные места вызова.

### Уроки стенда из сборки 37

* **В интерпретаторе нет `listp`, `numberp`, `atom`, `cadr`, `eq`,
  `type`.** Есть `car`, `cdr`, `nth`, `=`, `strcase`, `vl-some`,
  `vl-remove-if`. Проверка «это список?» средствами AutoLISP недоступна —
  поэтому разбор списка-вызова внутри `KG-Safe` сделать нельзя, и
  единственная защита — не передавать туда списки.
* **Точечные пары в стенде ведут себя не как в AutoCAD**: `vl-remove-if` и
  `KG-CdrCI` на списке точечных пар давали неверный результат (стиралась не
  та запись). Поддельные базы в тестах строятся из обычных списков.
* **Заглушка адаптера обязана повторять его контракт**, включая строковые
  ответы и коды отказа. Иначе тесты зелёные, а ветки обработки ответа не
  исполнены ни разу — именно так сборка 36 «прошла» 392 проверки с
  неработающей записью видимости.
* `KG-StrEq` приводит `nil` к пустой строке, а в этом интерпретаторе
  `(= "" "x")` истинно. В подделках сравнение ключей сделано своим
  `FAKE-SameKey`.

### Сборка 38: `0xC0000005` на первом шаге очистки — обход таблицы блоков

Прогон сборки 37 на реальном чертеже:

```
[шаг] очистка определений прошлой интеграции
=== INTCLEANUP: очистка определений прошлой интеграции ===
[шаг] очистка: карта ссылок; ошибка: Возникло исключение: 0xC0000005 (Нарушение доступа)
```

Падал первый же шаг очистки — `KG-EXRefHolders`, карта ссылок. Она
строилась обходом таблицы блоков: `tblnext "BLOCK"` → `tblobjname` →
`entnext` → `entget` по каждому определению. Тот же обход **до** вставки из
буфера проходил весь чертёж без ошибок (в трассировке видны все 111
определений). Падал он **после**: 48 переименований, два определения
вариантов, созданных копированием через ObjectDBX, и удалённый технический
экземпляр. Перехват исключение не ловит — `vl-catch-all-apply` вернул
ошибку, `KG-Safe` отдал `nil`, и очистка остановилась, не сняв ничего.

Обход таблицы блоков убран из очистки совсем. Карта ссылок строится одним
`ssget "_X" '((0 . "INSERT"))` — все вставки модели и всех листов — и
группой 330 у каждой: она указывает на запись блока, внутри которой лежит
вставка. Ни COM, ни `entnext` по чужим определениям.

Побочное решение: если владелец вставки не прочитался, ссылка всё равно
считается, а держатель показывается как «неизвестно». Держатель нужен
только для отчёта; решение принимает число ссылок, и потерять ссылку здесь
опаснее, чем показать неточное имя.

Если выборка не сработала (`ssget` вернул `nil`), карта не строится и
очистка останавливается с сообщением: без карты ссылок каждое определение
выглядит свободным. Пустой чертёж `ssget`'ом неотличим от отказа, поэтому
остановка считается правильным поведением.

### Чтение состояний вложенных блоков: второй путь и метка источника

В прогоне сборки 37:

```
Прочитано состояний вложенных блоков: 0
ВНИМАНИЕ: у заменённых экземпляров не прочитано ни одного состояния ...
```

и в трассировке **ни одной** метки `вложенная вставка "…"`. Значит, обход
анонимного представления не нашёл ни одной вложенной вставки — либо
вставка указывала не на `*U`, а прямо на определение. Различить эти два
случая по отчёту было нельзя, поэтому:

* чтение состояния вынесено в `KG_ScanDefInsertStates`, которая печатает
  `в определении "…" вложенных вставок: N, состояний прочитано: M`;
* если представления нет, состояния читаются из **родительского
  определения** — там лежат состояния по умолчанию, и именно они у
  экземпляра, свойства которого не меняли;
* источник чтения попадает в отчёт:
  `из них у представлений экземпляров (*U)` и
  `из них состояний по умолчанию из определения`;
* предупреждение «нет анонимного представления» печатается не более пяти
  раз: на чертеже со 100 экземплярами и 45 вложенными это 4500 одинаковых
  строк.

Состояния, прочитанные из определения, **не записываются** в новый
экземпляр: определение варианта общее для всех экземпляров, а состояние
нужно одному. Они показываются, чтобы было видно, что чтение работает.

### Уроки стенда из сборки 38

* **ename в стенде — строка, а `KG-OwnerBlockName` строку отсекает**
  (`(= (type e) (type ""))`). Поэтому держатель в тестах всегда
  «неизвестно», а сам `KG-OwnerBlockName` исполняется в
  `run_space_tests.py`, где ename — объект `Ename`.
* **Точечные пары обязательны там, где работает `KG-CdrCI`/`assoc`**: на

* **Служебный маркер нельзя класть ЭЛЕМЕНТОМ списка.** Маркер `"OK"` в
  списке карты ссылок приводил к тому, что `KG-CdrCI` «находил» любое имя:
  на строке сравнение срабатывало. Маркер живёт в `car` результата, карта —

* **`length` от строки в интерпретаторе даёт число знаков.** Поддельный

  ename, а `ssget` соблюдает фильтр по группе 0.
* **`handent` и `entget` — разные пространства имён** (handle → ename и
  ename → DXF). На одном словаре handle записи блока совпал с ename другой
  записи, и чтение имени определения давало `nil`.

**Мутационная проверка сборки 38:** убрать маркер `"OK"` — 1 провал
(T19.28); не считать ссылку, когда владелец не прочитался, — 3 провала
(T19.25, T19.26, T19.27b).

### Сборка 39: почему состояния вложенных блоков не переносились

`INTDUMP` на старом экземпляре дал полную картину:

```
Name: Комплект КП50 v1.4 стойка КП45303-2
IsDynamicBlock: T
DynamicProperties:
  Видимость1 = #<variant 8 Стоечная крышка (стеклопакет 32)>
  Отраженное состояние1 = #<variant 2 0>
Nested visibility:
[шаг] в определении "…" вложенных вставок: 85, состояний прочитано: 3
  Стойка КП50 контур            = #<variant 8 КП45303 70/45>
  Закладная в полость стойки    = #<variant 8 КП45492 44 мм>
  Стойка КП50                   = #<variant 8 КП45303 70/45>
```

Три факта, которые закрыли вопрос:

1. **Своих параметров видимости у вложенных блоков почти нет.** Из 85
   вложенных вставок состояния читаются только у трёх — `Стойка КП50`,
   `Стойка КП50 контур`, `Закладная в полость стойки`. Именно их и надо
   переносить; остальные вложения не динамические.
2. **Значение параметра приходит variant'ом.** `#<variant 8 …>` — это
   VT_BSTR. В предупреждении печатался variant, а сравнение со списком
   допустимых состояний такую пару не находило. `KG-GetVisibilityState`
   теперь разворачивает variant в строку.
3. **Имя вложения читается под старым именем.** Старые определения
   переименовываются в `…~до` **до** чтения старых экземпляров, поэтому
   вложенная вставка указывает на `Стойка КП50~до`, а в новом определении
   она называется `Стойка КП50`. Отсюда — все шесть «В новой версии такого
   вложенного блока нет, состояние не перенесено».

Добавлены `KG-StripDoSuffix` и `KG-NestedKeyMatch`: поиск вложенной
вставки в новом определении сравнивает имена с учётом суффикса `~до`
(T19.32–T19.35).

### `ssget "_X"` с фильтром вернул nil при живых вставках

```
[шаг] карта ссылок: выборка всех вставок
ОШИБКА: карту ссылок построить не удалось (вставок не найдено или выборка не сработала).
```

В чертеже было три вставки, выборка `ssget "_X" '((0 . "INSERT"))` ответила
`nil`, и очистка остановилась. Причина не установлена — поэтому добавлен
запасной путь: если выборка с фильтром не дала набора, делается выборка
**без фильтра** и группа 0 проверяется самим кодом (T19.30, T19.31). В
трассировку добавлены метки: какой путь сработал, что вернула выборка с
фильтром (набор / nil / текст ошибки), сколько объектов в наборе.

Если и запасная выборка вернёт nil, очистка по-прежнему останавливается:
без карты ссылок каждое определение выглядит свободным.

### Урок: на диск ушла непроверенная версия `KG-EXRefHolders`

Правка «маркер успешной выборки — в `car`, карта — в `cdr`» не записалась
(heredoc-патч упал на `assert`, файл не пишется), а тесты остались
зелёными: они читали карту через `(cdr REFH)` и не заметили, что на диске
лежит версия, где маркер — **элемент списка**, а карта теряется. Очистка с
такой версией получила бы пустую карту и объявила свободными все
определения.

Выводы:

* после патча сверять не только «тесты зелёные», но и **текст функции на
  диске** (`grep`/`sed` по имени);
* проверять надо **поведение**, а не форму: добавлен T19.28b — на карте со
  ссылками `KG-CleanupCandidates` не должен находить кандидатов. Форма
  результата (пара или плоский список) в AutoLISP средствами стенда не
  различается: `listp` и `atom` в интерпретаторе нет.

**Мутационная проверка сборки 39:** маркер элементом списка вместо пары —
4 провала; `KG-NestedKeyMatch` без снятия `~до` — 1 провал (T19.34).
Мутация «не проверять группу 0 в запасной выборке» тестами **не ловится**:
при `ed = nil` тело всё равно пропускается, поведение не меняется. Мутация
`KG-GetVisibilityState` (возвращать variant вместо строки) тоже не
ловится — в стенде этот адаптер заменён заглушкой, а в AutoCAD на нём
держится сравнение состояний; проверять его нужно по тексту предупреждений
в реальном прогоне.

### Сборка 40: две правки, которые «прошли тесты», но не попали на диск

Прогон сборки 39 на реальном чертеже дал две правды, которых тесты не
показали.

**1. `KG-NestedKeyMatch` была написана — и ни разу не вызвана.**
`grep -nF 'KG-NestedKeyMatch' Integration.lsp` по сборке 39 выдавал ровно
одну строку: 487 — это её определение. Вызова не было ни одного: патч,
который должен был заменить `KG-StrEq` на `KG-NestedKeyMatch` внутри
`KG-DefInsertByName`, на диск не записался. Тесты T19.32–T19.35 проверяли
саму функцию, а не то, что её кто-то зовёт, поэтому прогон был зелёный, а
чертёж снова дал шесть «не найден» с именами `Стойка КП50~до`.

**2. `consp "OK"` при повторном расчёте карты ссылок.** `KG-EXRefHolders`
возвращает пару `("OK" . карта)`; маркер снимался в одном месте, а
`holders` пересчитывается в четырёх (строки 3935, 4004, 4063, 4101 сборки
39). На втором пересчёте — сразу после стирания 37 сиротских `*U` — в
`KG-CleanupCounts` уходил список с `car` = строка `"OK"`, и AutoCAD падал с
«неверный тип аргумента: consp "OK"».

**Что сделано.** Сравнение в `KG-DefInsertByName` заменено на
`KG-NestedKeyMatch` (сравнение по ключу: `Стойка КП50~до` ↔ `Стойка КП50`).
Отсечение маркера перенесено из вызывающего кода в `KG-CleanupCounts` и
`KG-CleanupOrphans` — теперь оно работает во всех четырёх местах сразу, а
`KG-CleanupOrphans` дополнительно не считает `"OK"` определением.

**Два урока, из-за которых тесты не поймали ни того, ни другого.**

*Урок первый: «зелёный прогон» не доказывает, что правка на диске.*
После каждого патча нужно grep'ать **вызов**, а не определение: функция
может быть написана корректно и при этом не вызываться ни разу. Для этого
`KG-DefInsertByName` и `KG-EffectiveNameOf` перенесены выше строки
`(if (not KG-TESTING)` — до переноса их в стенде просто не существовало, и
тест, который должен был это поймать, падал с «не определена переменная:
KG_DEFINSERTBYNAME». Теперь T19.41/T19.42 гоняют настоящую функцию поверх
поддельной таблицы блоков, и мутация «вернуть `KG-StrEq`» даёт провал.

*Урок второй: стенд терпимее AutoCAD, и это скрывает падение.*
`(car "OK")` в интерпретаторе даёт `nil`, а в AutoCAD — «неверный тип
аргумента». Поэтому первый вариант теста на маркер ловил не мутацию, а
совпадение: `(length "OK")` в стенде = 2, и счётчик случайно совпадал.
Проверять надо наблюдаемое следствие — маркер просачивается в карту как
элемент с пустым именем (T19.39), — а не «падает / не падает».

**Заодно.** `nested-from-u` и `nested-from-def` считали экземпляры, а не
состояния: отчёт печатал «прочитано состояний 6», а ниже «1 / 1», и числа не
сходились. Теперь к ним прибавляется число состояний экземпляра, и сумма
`from-u + from-def` равна «прочитано состояний вложенных блоков».

**Мутационная проверка сборки 40:** `KG-NestedKeyMatch` → `KG-StrEq` —
1 провал (T19.41); убрать отсечение маркера в `KG-CleanupCounts` — 1 провал
(T19.39). Отсечение в `KG-CleanupOrphans` отдельной мутацией **не ловится**:
`"OK"` не проходит по `KG-IsAnonDynName` и в список сирот не попало бы и без
него — это защита на случай, когда карта приходит туда напрямую.

### Сборка 41: очистка не стёрла ничего, а `consp "OK"` вернулся

Прогон сборки 40 на реальном чертеже: интеграция прошла идеально —
`Восстановлено состояний видимости: 6`, `Прочитано состояний вложенных
блоков: 6`, `из них у представлений (*U): 3`, `из определения: 3`,
`Вложенных блоков не найдено: 0`, `Предупреждений: 0`, `Ошибок: 0`,
варианты `[OK]`. То есть перенос состояний вложенных блоков заработал.
А вот очистка дала две новые правды.

**1. `Стёрто сиротских *U: 0, не удалось: 43`.** `KG_HasMInsert` искала
многострочную вставку выборкой `ssget "_X"` с фильтром
`((0 . "INSERT") (66 . 1) (2 . имя))` — «вставка с атрибутами этого
определения». Анонимное представление динамического блока почти всегда
несёт атрибуты: тег представления `AcDbBlockRepBTag` хранится именно так.
Проверка отвечала «да» на все 43 сироты, `entdel` не вызывался ни разу.
Доказательство, что стирать было можно: следом `PURGE` снял 16 из этих 43
(`*U51`, `*U53`–`*U56`, `*U58`–`*U65`, `*U120`–`*U123`).

Теперь MINSERT ищется там, где он может быть, — внутри самого определения,
обходом `tblobjname` + `entnext` + `entget` до `ENDBLK` с проверкой группы
0 на `"MINSERT"`. Вставка с атрибутами больше не мешает (T19.48, T19.49).
Заодно в `KG_EXEraseAnonDef` появилась трассировка причины отказа —
«внутри есть многострочная вставка» / «BLOCK не найден» / «ENTD не отдал
определение» / «определение читается и после ENTD»: «не удалось: 43» без
причины и было тем, из-за чего дефект не было видно.

**2. `consp "OK"` вернулся — в другом месте.** В сборке 40 маркер снимался
внутри `KG-CleanupCounts` и `KG-CleanupOrphans`, а контроль после PURGE
печатал держателей, обходя карту напрямую: `(KG-CdrCI nm holders)`.
`KG-CdrCI` → `KG-AssocCI` → `vl-some` → `(car "OK")` — и AutoCAD падал.
Теперь маркер снимается там, где карта получена (`KG-Unmark`, три места

**Главный урок: стенд был терпимее AutoCAD, и это скрывало дефект дважды.**

аргумента: consp "OK"». Поэтому тесты, которые должны были ловить маркер в

убрано» падают ровно с той ошибкой, что была на чертеже.

Строгость едва не оказалась бутафорской, и это отдельный урок. Первая
версия строгих `car`/`cdr` поднимала ошибку через `vl-catch-all-apply`
внутри самой функции — то есть ловила собственное исключение и молча
возвращала `nil`. Вторая версия не работала по другой причине:
интерпретатор хранил `defun` под именем как оно написано (`car`), а вызывал
по имени в верхнем регистре (`CAR`), поэтому переопределение встроенной
функции не действовало вовсе. Обе версии выглядели включёнными. Теперь в

хелпер `_strict-fail`, а блок T0.1–T0.5 проверяет сам факт, что `car` от

### Сборка 48: `tblsearch` отдаёт запись без группы `-2`

Прогон сборки 47: интеграция снова безупречна (`=== ИТОГ: УСПЕШНО,

### Сборка 49: падение, место которого не покрыто метками

Прогон сборки 48 на чертеже с двумя старыми экземплярами: команда упала с
`ОШИБКА: неверная функция: T`, последний шаг — `вхождение 11B19:
динамические свойства`.

Разбор по коду места не дал. Метка «динамические свойства» ставится **до**
чтения свойств, а всё, что исполняется после неё, метками не покрыто:
`KG-GetDynamicProperties` целиком под `vl-catch-all-apply`, сама
`KG-InstanceModel` — под `vl-catch-all-apply` у вызывающего, и её отказ
должен был напечататься строкой `ВНИМАНИЕ: вхождение …`, которой в логе
нет. Стало быть, ошибка уходит мимо обоих перехватов, и по имеющемуся логу
её источник не определяется.

Что сделано — приборка, а не догадка:

* в `KG-CollectInstances` метки **после** каждого этапа: «вхождение
  получено как объект», «модель вхождения прочитана: да/ОШИБКА/nil». В
  следующий прогон последний шаг назовёт этап, а не его начало.
* вызов `KG_DBGetModel` в `INTEGRATE` обёрнут в `KG-Safe`: если снимок не
  прочитан, команда печатает `ВНИМАНИЕ: снимок чертежа не прочитан
  (<последний шаг>)` и продолжается с пустой моделью, а не обрывается,
  оставив имена освобождёнными.

Отдельная ловушка, найденная при написании приборки: `KG-IsErr` — это
`vl-catch-all-error-p`, и от живого vla-объекта он в AutoCAD сам бросает
«неверная функция». Метка, которая звала его напрямую и стояла **вне**
перехвата, уронила бы команду сама. Теперь оба вызова — под `KG-Safe`.

### Сборка 50: приборка шага 2 и первый тест на сбор вхождений

Приборка сборки 49 место сузила. Последняя метка — `модель вхождения
прочитана: да`, падение — до строки `вхождений прочитано`. Между ними шесть
выражений: проверка результата, печать предупреждения, разбор пространства,
добавление в список, счёт. Ни одно по коду не может дать «неверная функция:
T» — значит, отказ даёт то, что выглядит безопасным, и искать остаётся
перебором.

Что сделано:

* каждое из этих выражений — под своим `KG-Safe` и со своей меткой
  (`проверка результата чтения`, `печать предупреждения о вхождении`,
  `разбор пространства вхождения`, `вхождение добавлено в список`, `счёт
  вхождений`). В следующий прогон последний шаг назовёт выражение.
* отказ одного вхождения больше не обрывает команду: оно уходит в
  «пропущено», остальные дочитываются.
* `KG-CollectInstances` в `KG_DBGetModel` обёрнут в `KG-Safe`: при отказе
  печатается `ВНИМАНИЕ: вхождения не прочитаны (<последний шаг>)` и
  интеграция продолжается.
* найден и закрыт настоящий дефект рядом: `entget` в метке «чтение
  вхождения» стоял **вне** перехвата — на нечитаемом вхождении команда

### Сборка 51: ename определения лежал в группе −1

Прогон сборки 50 закрыл вопрос, который две сборки был гипотезой. Очистка
снова 19 раз ответила `BLOCK не найден`, а строка диагностики читалась как
`tblobjname -> nil, tblsearch -> запись без -2, COM -> nil`. Запись,
значит, возвращается, но ename не находится ни одним из трёх путей.

Причина: **имя сущности BLOCK в записи `tblsearch` лежит в группе −1**.
Группа −2 — это ename первого объекта *внутри* определения; у анонимного
представления её может не быть вовсе. Код брал только −2, поэтому ename не
находился никогда, `entdel` не звался, и 19 сиротских `*U` оставались в
чертеже. Именно они держали 41 определение с суффиксом `~до`, и PURGE не
мог снять ни то, ни другое: `*U` держит `~до`, `~до` держит `*U`.

Порядок путей теперь: `tblobjname` → `tblsearch (−2)` → `tblsearch (−1)` →
COM. Метка называет, какой путь сработал.

**Второе, отдельное.** В том же прогоне `INTEGRATE` напечатала
`=== ИТОГ: УСПЕШНО, замечаний нет ===` при `Заменено экземпляров: 0` — в
чертеже остались два экземпляра семейства, и отчёт этого не увидел.
Валидация ищет старые экземпляры по имени варианта, а определения к тому
моменту были переименованы и сняты. Признак такого состояния общий: у
вставки есть группа 2, а записи блока с этим именем нет. Добавлена
`KG-DanglingInserts` и строка `INTBRIEF`:
`Вставок с отсутствующим определением: N`. В норме ноль.

**Проверено:** `run_tests.py` 470/0 (T19.59–T19.61 — путь −1,
T20.8–T20.10 — вставки без определения), `run_space_tests.py` 45/0,
`check_load.py` — 13 команд, линтеры ALL PASS.
Мутации: отключить путь −1 → 2 провала; снять проверку наличия определения
→ 2 провала.

### Сборка 64: имя параметра видимости читается из словаря определения

Прогон сборки 63 закончился строкой `=== ИТОГ: УСПЕШНО ===`, но видимость
вложенных блоков у определений без итерации на чертеже по-прежнему равна
значению мастер-блока. В снимке прогона был признак, который до этого
считался особенностью данных:

```
[шаг] снимок состояний вложенных блоков: определений 7, состояний 27
Стойка КП50                  вложенных 4, состояний 0
Стойка КП50 контур           вложенных 6, состояний 0
Закладная в полость стойки   вложенных 5, состояний 5
```

У двух определений состояний нет ни до, ни после. Не «снялось и не
вернулось», а **не снималось вовсе** — возвращать было нечего, и отчёт
«возвращено 5, отказов 0» был правдив.

Причин оказалось две.

**1. Параметр видимости искали по написанию имени.** Эвристика
`(wcmatch (strcase имя) "*ВИДИМ*,*VISIB*")` — единственная дорога к
свойству. У «Стойка КП50» параметр назван иначе, шаблону не подходит, и
`KG-GetVisibilityState` возвращал nil для каждой вложенной вставки.

Имя параметра в динамическом блоке хранится в словаре расширения записи
BLOCK: `ACAD_ENHANCEDBLOCK` → группа 360 (указатель на параметр) →
группа 301 (имя). Добавлены:

| Функция | Что делает |
| --- | --- |
| `KG-VisParamName` | имя параметра видимости из словаря определения |
| `KG-FindDynPropByName` | свойство по точному имени (`vla-get-PropertyName`) |
| `KG-FindDynPropBy` | свойство по эвристике: есть `AllowedValues` и имя похоже на «видим»/«visib» |
| `KG-FindVisibilityProperty` | сначала точное имя, потом эвристика |
| `KG-VisibilityPropertyOf` | единая точка: имя из словаря → свойство |

`KG-GetVisibilityState`, `KG-SetVisibilityState` и
`KG-GetAllowedVisibilityStates` переведены на `KG-VisibilityPropertyOf`;
до этого каждая из них звала эвристику напрямую.

**2. Запасной поиск подменял основной.** `KG-FindDynPropBy` тоже сверяла
точное имя (`(or (and want (KG-StrEq nm want)) (wcmatch ...))`). Из-за
этого мутация «имя из словаря не используется» не меняла результата и
тест её не ловил: свойство всё равно находилось по имени, только на
запасном пути. Сверка точного имени из `KG-FindDynPropBy` убрана — это
задача `KG-FindDynPropByName`, у запасного пути осталась только эвристика.
Аргумент `want` у `KG-FindDynPropBy` снят.

**3. Определения по схеме семейства больше не пропускаются.** Шаг возврата
исключал их условием `(not (KG-ParseBlockName nm))`: казалось, состояниям
семейства довольно переноса по экземплярам в шаге замены. Это неверно —
шаг замены пишет в анонимное представление `*U` живого экземпляра, а
содержимое самого определения остаётся пришедшим из буфера. Отсюда
«при редактировании блока открывается состояние мастер-блока»: два разных

### Сборка 63: запись состояния проверяется чтением, отчёт называет определения

Прогон сборки 62 дал числа, которые не сходятся с тем, что видно на чертеже:

```
[шаг] снимок состояний вложенных блоков: определений 7, состояний 27
[шаг] возвращено состояний вложенных блоков: 5
Возвращено состояний вложенных блоков в определениях: 5
  из них не найдено в новой версии: 0
  из них записать не удалось: 0
```

Наблюдение пользователя: блок, принявший версию мастер-блока, при открытии для
редактирования показывает видимость вложенного динамического блока как у
вставляемого мастер-блока; при вставке такого блока через «Вставить блок»
видимость вложенных тоже как у мастер-блока. То есть состояние не применилось,
хотя отчёт показал ноль отказов.

**Причина в том, что считать.** `KG-SetVisibilityState` отдаёт успех, когда
`vlax-put-property` не бросил исключение. Вложение лежит внутри определения, и
AutoCAD не обязан применять к нему динамическое свойство так же, как применяет
к экземпляру в модели. «Вернулось 5» означало «пять вызовов прошли», а не «пять
состояний стоят».

**Что добавлено.**

* `KG-VerifyNestedVis` — после записи состояние читается обратно и
  сравнивается с тем, что писали. Несовпадение считается отдельно:
  `из них запись не подтвердилась чтением`.
* Отчёт называет определения, в которые состояния возвращены, а не только
  количество: `Определений, в которые возвращены состояния: 1` и список.
* С подробной печатью каждое состояние печатается парой
  `вложенный="прежнее" -> "стало"`, а не принятое — с пометкой `НЕ ПРИНЯТО`.
* В снимке появилось число `без параметра видимости N` — сколько вложенных
  вставок осталось без состояния. Считается от числа вложенных вставок, а не
  от числа пар без состояния: чтение свойств может вообще не отдать пару для
  вставки без параметра видимости, и тогда пропуск не был бы виден. Без этого
  числа «снято 27» и «в определении 9 вложенных вставок, состояний 9» не
  свести с «вернулось 5».

**Тесты T22.17–T22.20** (добавлены к T22.1–T22.16 и T22.4a–T22.4c):
неподтверждённая запись не считается возвратом, считается отдельным числом,
определение называется в отчёте, вложенные вставки без состояния посчитаны.

Мутации:

| Мутация | Провалов |
|---|---|
| проверка чтением убрана | 2 |
| неподтверждённая запись считается возвратом | 2 |
| определения не называются | 1 |

**Что эта сборка НЕ исправляет.** Она делает видимым, где именно состояние не
применяется. Если AutoCAD не даёт писать динамическое свойство вложению внутри
определения, следующим шагом придётся менять способ: либо писать состояние до
подмены определения, либо переносить его вместе с содержимым. По числам из
прогона сборки 63 станет видно, какой из двух случаев перед нами.

Также не обработаны другие динамические свойства вложенных блоков (растяжение,
поворот, массив) — сохраняются и возвращаются только состояния видимости.

### Сборка 62: видимость вложенных блоков возвращается определениям без итерации

Прогон на чертеже, куда одновременно вставили три мастер-блока разных типов
(`Комплект КП50 v1.51`, `Комплект КП50К ригель v1.52`, `Комплект КП50К стойка
v1.51`), дал полный блок `=== Результат ===` впервые на реальном чертеже:

```
Кандидатов на освобождение: 44      Освобождено имён до вставки: 44
Из них занято пришедшими: 42        Из них вернулось на место: 2
Пришло определений из буфера: 182   Обновлено вложенных определений: 40
Заменено экземпляров: 2             Создано вариантов: 1
Вариант "": 1/1 OK                  Вариант "КП45387": 1/1 OK
=== ИТОГ: УСПЕШНО, замечаний нет ===
```

Чужое семейство `Комплект КП50К` не тронуто, как и требуется. Очистка сняла
34 + 17 + 5 = 56 блоков; осталось одно определение `_Oblique~до` и 32
сиротских `*U`.

**Два наблюдения пользователя по этому прогону.** Блоки с итерацией в имени
сохраняют правильную видимость вложенных блоков. Блоки без итерации
подменяются корректно, но исходную видимость теряют.

**Причина.** Определение без итерации подменяется целиком: старое
переименовывается в «имя~до», из буфера приходит новое под прежним именем.
Состояния видимости вложенных блоков при этом сбрасываются в значения по
умолчанию новой версии. У блоков с итерацией состояния переносятся по
экземплярам в шаге замены, поэтому они и сохранялись.

**Что добавлено.** Шаг 8в — `KG-Step_RestoreNestedVis`:

* `KG-SaveNestedVis` снимает состояния вложенных блоков **до** освобождения
  имён — после переименования определение живёт под служебным именем, а
  вернуть состояние нужно определению под прежним;
* определения без вложенных вставок до COM-чтения свойств не доходят
  (`KG-DefNestedVisOf`): на крупном чертеже их большинство, а чтение свойств
  — самая дорогая часть обхода;
* `KG-Step_RestoreNestedVis` возвращает состояния после перепривязки, когда
  вложенные вставки уже указывают на прежние имена;
* обрабатываются только переименованные пары, определения по схеме семейства
  пропускаются — у них состояния переносятся по экземплярам;
* отчёт показывает три числа: возвращено, не найдено в новой версии, записать
  не удалось.

**Попутно исправлено вводящее в заблуждение сообщение.** Шаг 8б на этом
прогоне напечатал `ВНИМАНИЕ: не удалось перепривязать за 12 проходов:` и
список из 43 имён при `Перепривязано ссылок: 0`. Отказа не было:
переименование через `vla-put-Name` уже увело ссылки за именем, возвращать
было нечего. Предупреждение теперь печатается только когда есть пропуски
из-за риска зациклить определение.

**Тесты T22.1–T22.16** (18 проверок): состав снимка, пропуск определений без
вложенных вставок, возврат, «не найдено в новой версии», отказ записи,
исключение семейства, исчезнувшее определение, пустая пара.

Мутации, которые тесты ловят:

| Мутация | Провалов |
|---|---|
| состояния не возвращаются вовсе | 4 |
| семейство не исключается | 2 |
| исчезнувшее определение обрабатывается | 2 |
| отказ записи считается возвратом | 2 |
| состояния не записываются | 3 |
| COM-чтение для всех определений | 1 |

Две дыры в тестах закрыты по ходу: исключение семейства сначала
проверялось там, где срабатывала другая проверка (вложенного блока не было в
заглушке), а пропуск определений без вложенных вставок не отличался от
«состояний нет» — добавлен счётчик обращений к COM-чтению.

**Не проверено в AutoCAD:** запись свойства видимости вложению, которое лежит

внутри анонимных представлений `*U` и это работает; запись внутрь обычного
определения — тот же вызов, но на реальном чертеже не выполнялся.

### Сборка 61: ссылки на прежние имена возвращаются внутри чужих определений

Задача: вносимый мастер-блок приносит более свежую версию блоков, и
одноимённое определение должно обновиться по всему чертежу — не только там,
где его вставляют в модель.

**Что уже работало.** До вставки из буфера `C:INTEGRATE` освобождает имена
всех пользовательских определений чертежа (`освобождение имён до вставки:
кандидатов N`), вставка приносит определения под прежними именами, а то, что
буфер не принёс, возвращается на место. На прогоне это видно как
«Освобождено имён 44, занято пришедшими 41, вернулось 3».

**Чего не хватало.** Переименование через `vla-put-Name` уводит за именем
ссылки AutoCAD, но на реальном чертеже после прогона осталось 31 определение
«имя~до» с нулём вставок, и PURGE их не снял. `Своих без вставок
(кандидаты): 31` при `Вставок с отсутствующим определением: 0` — значит,
ссылки на них были, но не такие, которые видит карта ссылок.

**Что добавлено.** Шаг 8б — `KG-Step_RewireDefs`:

* держатели ищутся обходом содержимого всех определений таблицы, включая
  анонимные представления (`KG-DefRefHolders`, кэш `KG-REWHOLD`);
* у найденных вставок группа 2 переписывается на прежнее имя через `entmod`
  (`KG-RewireDefRefs`);
* шаг проходит пары по кругу — ссылка внутри определения, которое само стало
  прежним только на этом проходе, находится на следующем;
* предел 12 проходов: две пары, ссылающиеся друг на друга, иначе крутились бы
  вечно;
* определение не правится, если после правки оно замкнулось бы само на себя
  (`KG-WouldCycle`, обход в ширину по графу **после** перепривязки —
  `KG-RewResolve` приводит служебные имена к прежним). Про такие печатается
  предупреждение, и они попадают в `Оставлены как есть`.

Отчёт дополнен строками `Перепривязано ссылок на прежние имена: N` и
`Оставлены как есть (риск зациклить определение): N`. `INTBRIEF` называет

**Три настоящие ошибки, найденные при написании шага.** Все три стенд

### Сборка 59: предупреждение печатало причину чужого отказа

Прогон сборки 58 напечатал подряд:

```
[счёт] определений в списке: 57
ВНИМАНИЕ: не напечаталось число определений (шаг "счёт вхождений", неверная функция: T), значение: 57.
```

Счётчик напечатался — и предупреждение всё равно вышло. Две мои ошибки
в одной строке:

1. Условие было `(if (KG-Safe ... nil) ...)`. В LISP любое непустое
   значение истинно, поэтому `(not …)` не отличало отказ от успеха:
   лямбда возвращала `t`, ветка «не напечаталось» выполнялась всегда.
2. `KG-Safe` не сбрасывал `KG-FAIL-STEP`, и в строку попала причина
   отказа, случившегося раньше и в другом месте. Отсюда «шаг "счёт
   вхождений"» рядом со значением 57.

Побочный результат полезный: **настоящий отказ назван.** `KG-FAIL-STEP`
стоял на «счёт вхождений», а строки «вхождений прочитано: N» в логе нет
ни разу за четыре чтения модели. То есть `неверная функция: T` происходит
в хвосте `KG-CollectInstances`, где четыре вызова стояли под одним
перехватом.

Что сделано:

- `KG-Safe` сбрасывает `KG-FAIL-STEP` / `KG-FAIL-MSG` **до** операции;
- условие предупреждения — по флагу `KG-CNT-OK`, а не по значению;
- хвост `KG-CollectInstances` разбит на три этапа под отдельными
  перехватами: метка, строка со счётчиком, счётчики пропусков. Каждый
  отказ называется своим предупреждением;
- добавлена строка `[счёт] вхождений прочитано: N` — её не было, поэтому
  отказ и оставался невидимым.

**Проверено:** `run_tests.py` 496/0. T20.36–T20.39 — удачный вызов не
несёт причину чужого отказа. Мутация «`KG-Safe` не сбрасывает прошлый
отказ» → 2 провала. `run_space_tests.py` 45/0, три линтера ALL PASS,
13 команд.

### Сборка 58: счётчик отделён от печати

Единственный отказ в том прогоне — косметический, но неназванный:

```
[шаг] таблица блоков прочитана
ВНИМАНИЕ: не напечаталось число определений (шаг "таблица блоков прочитана", неверная функция: T).
```

шесть раз подряд, при полностью успешной интеграции. Строка состояла из
четырёх вызовов под одним перехватом — `length`, `KG-NumStr`, `strcat`,
`KG-Trace`, — и какой из них отказал, видно не было.

Теперь подсчёт и печать разделены:

```
(setq KG-DEFCOUNT (KG-Safe '(lambda () (length defs-l)) nil))
... (princ (strcat "\n[счёт] определений в списке: " (KG-AsString KG-DEFCOUNT)))
```

Отказ преобразования в строку больше не уносит значение, а предупреждение
печатает само значение. Подозрение на `KG-NumStr`: он идёт через
`KG-AsNum -> KG-Num -> (type x)`, а `type` от неожиданного значения —
кандидат на тот же «неверная функция: T». **Это гипотеза, не вывод.**

**Проверено:** `run_tests.py` 492/0. T20.33–T20.35 — подсчёт переживает
отказ преобразования, отказ назван, а без отказа число преобразуется.
Честно: это проверка ПРИЁМА, а не самого места в `KG_DBGetModel` — она
по-прежнему внутри `(if (not KG-TESTING) ...)` и на стенде не вызывается.
Заглушка на `type` невозможна: её зовёт `KG-AsString`, попытка дала
бесконечную рекурсию. Мутация «`KG-Safe` не выполняет операцию» роняет
весь стенд, поэтому на этих тестах не проверялась.
`run_space_tests.py` 45/0, три линтера ALL PASS, 13 команд.

### Сборка 57: предупреждение называло не то место, а отказ стоил всей модели

Прогон сборки 56 на новом реципиенте дал три строки подряд:

```
[шаг] чтение таблицы блоков
[шаг] таблица блоков прочитана
ВНИМАНИЕ: снимок чертежа не прочитан (таблица блоков прочитана).
```

Первая ошибка моя, в диагностике. `KG-Safe` возвращал запасное значение, а
причину печатали как `KG-LAST-STEP`. Но `KG-Trace` и `KG-Mark`
перезаписывают `KG-LAST-STEP` на каждом удачном шаге, поэтому к моменту
предупреждения там стоял шаг, пройденный ДО отказа. «таблица блоков
прочитана» — это то, что удалось, а не то, что сломалось.

Вторая ошибка дороже. `KG_DBGetModel` не вернула ничего, и все вызовы под
`KG-Safe` получили `nil`. Отчёт остался без данных и напечатал:

```
Экземпляров семейства в чертеже: 0
ОШИБКА: Определение мастер-версии "Комплект КП50 v1.51" не найдено в чертеже.
```

при том, что мастер-блок в чертеже был — вставка из буфера прошла, и та же
команда чуть выше нашла его и прочитала 83 вложенные вставки. Пустая модель
дала «не найдено», а не «не прочитано».

Что сделано:

- `KG-Safe` запоминает шаг и сообщение отказа в `KG-FAIL-STEP` /
  `KG-FAIL-MSG`; предупреждения печатают их через `KG-FailText`;
- строка со счётчиком определений и сводка пропущенных в `KG_DBGetModel`
  перехвачены: печать не должна стоить результата. Прогон оборвался ровно
  между меткой «таблица блоков прочитана» и этой строкой;
- добавлена метка `сбор вхождений` перед `KG-CollectInstances`;
- **модель возвращается всегда**: отказ сбора вхождений оставляет пустой
  список вхождений, но определения в модели остаются.

**Причина отказа по-прежнему не названа** — теперь её назовёт сам лог:
в скобках будет шаг, на котором случилось, и сообщение AutoCAD.

**Проверено:** `run_tests.py` 489/0. T20.29–T20.32 — шаг отказа
запоминается и печатается, пройденный до него шаг в причину не попадает.
Мутация «`KG-FAIL-STEP` не запоминается» → 1 провал; мутация «печатать
последний шаг, как в сборке 56» → 1 провал. Второй тест сначала мутацию не
ловил: в нём между отказом и печатью не было удачного шага, который
перезаписал бы `KG-LAST-STEP`. `run_space_tests.py` 45/0, три линтера
ALL PASS, 13 команд.

### Сборка 56: отказ одного определения обрывал всю команду

Прогон сборки 55 на новом реципиенте (100 блоков) остановился так:

```
[шаг] снимок чертежа до изменений
[шаг] чтение таблицы блоков
ОШИБКА: неверная функция: T
Последний шаг: чтение определения "*U87"
```

Раньше в том же прогоне, до вставки из буфера, первый снимок тоже не
прочитался — но дал только предупреждение:

```
ВНИМАНИЕ: снимок чертежа не прочитан (чтение определения "*U54").
Интеграция продолжена без него.
```

Разница была не в причине, а в том, перехвачен ли вызов. Первый снимок
в `C:INTEGRATE` шёл под `KG-Safe`; второй, в `KG-Integrate_Model` —
напрямую. Отказ одного и того же чтения в одном месте стоил предупреждения,
в другом — команды, оборванной после вставки из буфера и с освобождёнными
именами.

Что сделано:

- чтение свойств каждого определения в `KG_DBGetModel` теперь сообщает об
  отказе именем и причиной и переходит к следующему определению;
- список пропущенных виден в `KG-SKIP-DEFS` и печатается сводкой
  (`Определений не прочитано и пропущено: N` + до 10 имён);
- обход содержимого в `KG-DefNestedRefs` и чтение состояний в
  `KG-DefVisStates` перехвачены целиком — отказ на одном вложенном объекте
  отдаёт уже найденное;
- все вызовы `KG_DBGetModel` внутри интеграции переведены под `KG-Safe`
  с запасной пустой моделью и предупреждением;
- проверка результата COM-вызова вынесена в `KG-IsErrSafe`: сам
  `(vl-catch-all-error-p)` от неожиданного значения бросает ту же
  «неверная функция: T», и без перехвата проверки последняя метка
  указывала бы на уже пройденное место;
- добавлена метка `таблица блоков прочитана` ПОСЛЕ цикла. Без неё
  `чтение определения "X"` оставалась последней меткой и при отказе в самом
  обходе коллекции, то есть указывала не туда.

**Источник `неверная функция: T` по-прежнему не назван** — перехват не
объясняет причину, он не даёт ей оборвать команду. Имя определения в
предупреждении — это данные для следующего шага.

**Честно о проверке:** теста на это нет. Настоящая `KG_DBGetModel` лежит
внутри `(if (not KG-TESTING) ...)`, а в `tests.lsp` есть её заглушка
`(defun KG_DBGetModel () *DB*)`. Попытка написать стендовый тест дала
18 определений вместо двух — это `*DB*`, а не модель чертежа: проверка
звала заглушку и всегда отвечала бы «хорошо». Фиктивные T20.21–T20.25
удалены, причина записана комментарием в `tests.lsp`. Теста на ветку
отказа в `KG-IsErrSafe` тоже нет: заглушка на `vl-catch-all-error-p`
роняет весь прогон, её зовёт `KG-IsErr`. Есть только T20.26 на нормальную
ветку — мутация «`KG-IsErrSafe` всегда отдаёт запасное» на нём ловится.

Проверено: 485/0, 45/0, три линтера ALL PASS, 13 команд.

### Сборка 55: лог свёрнут, подробности — отдельным флагом

Повод — переход на реципиента со 100 блоками. По данным прогона сборки 54
(2 экземпляра) лог давал 764 построчных вывода; при 100 экземплярах только
вложенных вставок было бы 8300 строк (по 83 на экземпляр), всего около
10 000. Такое сообщение не отправить, и присылали только хвост — а причина
каждый раз оказывалась в начале.

Добавлен второй уровень трассировки, `KG-TRACE-DETAIL` (по умолчанию `nil`)
и функция `KG-TraceDetail`. Она **всегда** запоминает последнее действие в
`KG-LAST-STEP`, но печатает только при включённом флаге: место падения
определяется и без подробной печати.

На подробный уровень переведены 27 меток: чтение каждого определения,
каждая вложенная вставка, 8 полей вхождения, каждое переименование, каждая
попытка стирания `*U` вместе с причиной, успех `KG-DefEnt`.

Списки имён печатаются через `KG-SayList` / `KG-PrincList`: счётчик, первые
10 имён, дальше `... и ещё N`. Полностью печатаются только отказы —
в частности, блок `ОСТАЛИСЬ СТАРЫМИ` вынесен отдельно и не сворачивается.

Заодно исправлена метка, которая вводила в заблуждение: `стирание "…":
BLOCK не найден` печаталась, когда ename **найден**, а не отдался `entdel`.
Теперь это `ENTD не отдал определение`, а `не найден ename определения` —
отдельный случай. В прогоне сборки 54 строка `нет BLOCK для "…"` не
появилась ни разу, то есть поиск определения работал, а читался отказ как
«определения нет».

## 7. Проверенные факты о платформе

Эти выводы получены по документации и обсуждениям AutoCAD и определяют
архитектуру решения:

* **Динамические блоки нельзя создавать и структурно изменять из LISP.**
  `getdynamicblockproperties` читает и меняет только значения уже
  существующих параметров. Поэтому определения вариантов, создаваемые из
  мастер-версии, деградируют до статических — это сообщается в отчёте.
* **`PASTECLIP` не переопределяет существующие определения.** Он печатает
  «Duplicate definition of block … ignored» и подставляет уже имеющееся
  определение; вставка динамического блока при совпадении имени сбрасывает
  его в состояние по умолчанию. Отсюда шаг «освободить имена до вставки».
* **Суффикс `$0$` — не результат вставки.** Он появляется при привязке
  XREF (`XBIND`) и в `etransmit`. Ранний план «вставить → переименовать
  `ИМЯ$0$`» на этом основании отброшен.
* **Анонимные определения `*U…` переименовываются через `vla-put-name`, но
  у динамических блоков это разрывает связь с родительским определением.**
  Поэтому анонимные определения не переименовываются.
* **Эффективное имя** читается через `vla-get-EffectiveName`, с запасным
  путём через `tblobjname` + XDATA `AcDbBlockRepBTag` + `handent` по коду 1005.
* **`-INSERT имя=файл` и Design Center «Redefine only»** переопределяют
  определение на месте, но требуют файл — по ТЗ этот путь исключён.
